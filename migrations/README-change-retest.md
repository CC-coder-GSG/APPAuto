# 最终测试中的需求变更重测

最终测试需求卡片出现关联测试任务变更时，可以点击「处理变更」。成员可以查看任务及变更内容；具有「需求分配」权限的人员可以选择任务、负责人并派发重测。

- 默认重新激活、指派原任务并将其暂停，跨版本也保留原任务编号及所属执行，不代替接手人确认需求变更。派发不提交工时、不启动本地计时，接手人确认变更并开始测试后才计时；暂停未经回读确认不会报派发成功。
- 旧大版本任务可另选「在当前大版本新建重测任务」，仅在明确选择该方式后创建副本。
- 对旧版已经新建过任务的变更，可再次打开「处理变更」切回原任务。已有新任务保留在禅道；本轮需求进度改为跟踪原任务，保留此前新任务编号及上一轮测试记录，不自动删除或取消已有任务。
- 负责人建议优先读取关闭前的指派历史，其次使用当前指派人、上次完成者；无法确定时必须手动选择。下发前校验当前执行可指派人员。
- 派发成功后，归档所选负责人上一轮的用例完成、测试完成、正在测试及完成时间，并重置其本轮勾选。其他人员及其他需求的记录保持原样。历史记录可在弹窗查看。
- 负责人阅读并确认变更后，通过现有任务流程测试、完成任务，并勾选本轮用例完成。重测记录只有在任务确认最新需求、任务完成且负责人本轮两项均完成时，才显示「重测完成」。重测未结束前，需求卡片不会显示整体完成。

跨版本原任务只有在该需求的有效变更重测记录明确关联后，才加入当前需求工作台的可操作任务范围；任务操作仍实时核对原所属执行、研发需求、任务类型及当前指派人。此调整不需要数据库结构升级。

最终测试中，当前用户负责且尚未测试完成的变更重测需求保持流光边缘，阅读、悬停或清除未读提醒不会取消；完成本轮任务和测试勾选后取消强调。减少动态效果偏好下保留静态描边。确认需求变更采用增量刷新，保留卡片展开状态，并按卡片位置保持页面或内层滚动区域的位置。

任务操作在前置读取失败时返回 `X-Operation-Outcome: not-started`，前端据此允许显式重试，不把未发送的修改当作未知写入。详情接口故障时可从同账号的实时执行任务列表恢复读取，仍校验任务编号、所属执行、研发需求及当前指派人；不使用缓存状态代替远端确认。真正结果未知的写入保持防重保护，核对有进度及次数提示，20 秒超时后可以再次核对，不会自动重发写入。

## 可靠性

派发按需求加跨进程锁，按「需求、源任务、需求版本」保存唯一派发凭据。超时重试会读取禅道状态；新建任务通过唯一标记找回，避免重复建任务。成功项不会在弹窗重试时再次提交。

如果创建请求结果不明确，且重试仍无法找到对应任务，会保留「派发待核实」，要求核对禅道，不自动再发创建请求。远端恢复/指派未经读取确认前，不重置个人勾选。所有派发操作记录审计日志，已提交工时不会重复上报。

### 创建失败与重试修复

新建重测任务必须填写预计开始、结束日期，前后端会在派发前校验，并传给禅道。禅道明确拒绝的创建请求记录为「派发失败，可重试」，保留安全的错误摘要，例如未通过校验的字段名；修正后复用原派发凭据重试。

旧版留下的「派发待核实、无任务编号」记录也可恢复：先核对禅道任务，再勾选「确认未创建，允许重新派发」。后端会重新读取当前执行的完整任务列表，通过原唯一标记优先找回已有任务；未找到且用户明确确认后才重新创建。列表读取失败、发现多个匹配任务或关联校验失败时均不会创建。错误阶段与安全摘要保存在现有派发记录中，无需新增数据库迁移。

## 部署

此功能新增 `requirement_change_retests` 表。SQLite 沿用启动时的建表流程；PostgreSQL 在发布应用前执行 `alembic upgrade head`，目标结构版本为 `20261113_01`。此迁移仅新增表、索引和外键，不修改既有业务行。应用运行账号需要新表及其序列的读写权限。

部署后，在 V4.0.5.0 的最终测试需求卡片中找到 r#4030，点击「处理变更」，核对各任务所属版本、负责人及需求版本差异后选择派发。开发及自动化测试不修改线上禅道任务。

## 验证

后端：`tests/test_requirement_changes.py` 覆盖恢复、跨版本创建、版本及权限校验、历史归档、远端结果未生效、超时恢复、完成判定和 API。

浏览器：`tests/requirement_changes.spec.cjs` 使用真实工作台和弹窗模块、拦截全部网络，覆盖变更需求完成标记、负责人校验、转义、逐项结果、失败重试及只读权限。另运行原多任务工作台浏览器回归。
