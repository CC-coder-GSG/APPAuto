## 问题 1：时间显示比本地时间慢 8 小时

### 根本原因

全项目所有模型（`bug.py`、`stage5.py`、`user.py` 等共 20+ 处）均使用 `datetime.utcnow()` 记录时间。`utcnow()` 返回 UTC 时间（格林威治时间），比中国标准时间（UTC+8）慢 8 小时。SQLite 存储的是不带时区信息的 naive datetime，后端在格式化后直接返回给前端，前端也没有做时区转换，因此用户看到的时间始终比实际时间早 8 小时。

### 影响范围

- 整体测试页"同步时间"徽标
- 报表中心各时间戳
- 数据大盘"创建时间"
- 活动中心操作日志时间
- 构建记录时间
- 所有 `created_at` / `updated_at` 字段的展示

### 整改方案

**推荐方案（最简、改动最小）：**  
将所有模型的 `default=datetime.utcnow` 和服务层的 `datetime.utcnow()` 调用改为 `datetime.now()`，使用操作系统本地时间（服务器已处于 UTC+8 环境，`datetime.now()` 直接就是北京时间）。

需要修改的文件（共约 40 处）：
```

app/models/build_record.py

app/services/export_service.py
app/services/feedback_service.py
app/services/push_service.py

app/services/zentao_auth_service.py
app/services/zentao_sync_service.py
app/api/routes/admin.py
app/api/routes/zentao_bug_actions.py
```

**注意：** 不修改已有历史数据（存量数据的时间戳差了 8 小时，修复代码后新写入的数据会正确）。若需要存量数据也正确，需要对数据库中所有时间字段执行一次 `UPDATE table SET field = datetime(field, '+8 hours')`，这属于数据迁移，需谨慎评估。

## 问题 2：整体测试每条 Bug 下方第四个徽标（显示时间）的作用

### 调研结论

整体测试页每条 Bug 的标题列下方会显示最多四个徽标（均为有数据时才显示），顺序如下：

| 顺序 | 徽标内容 | 字段来源 | 含义 |
|------|---------|---------|------|
| 1 | `同步 2026-04-17 10:30` | `last_zentao_synced_at` | 本系统最近一次从禅道同步该 Bug 数据的时间 |
| 2 | `当前指派 张三` | `zentao_assigned_to_name` | 当前在禅道上 Bug 指派给谁 |
| 3 | `禅道关闭 李四` | `zentao_closed_by_name` | 由谁在禅道上执行了关闭操作 |
| **4** | `2026-04-15 14:22` | `zentao_close_date` | **Bug 在禅道上被关闭的时间** |

**第四个时间徽标 = 禅道关闭时间**，即该 Bug 在禅道端被正式关闭（closed）的日期时间。其来源是禅道同步时拉取的 `closedDate` 字段，存储在本地 `BugTracking.zentao_close_date`，仅在 Bug 状态为 closed 且有关闭时间时才会显示。

代码位置：`frontend/js/tabs/stage5.js` 第 190 行
```javascript
const closeDateMeta = b.zentao_close_date
  ? `<span class="badge" ...>${escapeHtml(b.zentao_close_date)}</span>`
  : '';
```

### 备注
四个徽标只在对应数据存在时才显示，未关闭的 Bug 不会显示第 3、4 个。

## 问题 4：Bug 编辑功能是否同步修改禅道

### 调研结论

分两种情况：

**① 禅道 Bug（有 zentao_bug_id 的）**

点击"编辑"会：
1. 通过 `PUT /zentao/bugs/{zt_id}` 同步修改**禅道上的 Bug 标题**；
2. 同时把本地 `BugTracking` 表中 `zentao_bug_title` 字段也更新。

**结论：会同步修改禅道。**

**② 纯本地 Bug（无 zentao_bug_id 的）**

点击"编辑"只修改本地 `bug_id`（Bug 编号纠正功能）。

**结论：不涉及禅道，仅改本地。**

**当前限制：** 不论哪种情况，目前"编辑"功能只支持修改**标题/编号**这一个字段。严重度、优先级、指派人等字段均不可编辑。

## 问题 5：指派人名单加载不出来（重要 Bug）

### 根本原因（已确认）

这是一个代码 Bug，**所有需要从禅道页面 JSON 获取用户列表的功能**（创建 Bug 弹窗、激活 Bug 弹窗、关闭 Bug 弹窗等）均受影响。

**禅道页面 JSON 接口返回的是双层编码格式：**
```json
{
  "status": "success",
  "data": "{\"users\":{...}, \"builds\":[...], ...}",
  "md5": "xxx"
}
```

`data` 字段是一个 **JSON 字符串**，需要二次 `json.loads()` 才能得到实际的 `users` / `builds` 等数据。

但现有代码在 `get_page()` 返回后直接调用 `meta.get("users")`，而 `meta` 是外层对象（只有 `status`/`data`/`md5` 三个键），`meta.get("users")` 始终为 `None`，导致用户列表为空。

**验证过程：**
- 直接请求 `bug-create-15-1578.json`：返回 267 个用户，build 列表正常；
- 通过当前 `get_page()` → `meta.get("users")`：返回空字典。

### 影响范围

| 功能 | 受影响情况 |
|------|----------|
| 新建禅道 Bug 弹窗（指派人列表） | 始终为空 |
| 激活 Bug 弹窗（指派人列表） | 始终为空 |
| 关闭 Bug 弹窗（信息不完整） | 数据缺失 |
| 禅道 Bug 操作元数据 | 全部缺失 |

### 整改方案

在 `app/services/zentao_client_service.py` 的 `get_page()` 方法末尾，添加自动解包逻辑：

```python
def get_page(self, path: str, params: dict | None = None) -> dict | None:
    ...
    result = resp.json()
    # 禅道页面JSON返回双层结构: {"status":"success","data":"escaped_json_string"}
    # 自动解包 data 字段
    if isinstance(result, dict) and isinstance(result.get("data"), str):
        import json as _json
        try:
            return _json.loads(result["data"])
        except Exception:
            pass
    return result
```

此改动只需修改一处，所有依赖 `get_page()` 的功能（create-meta、action-meta）均自动修复。

## 问题 6：有了禅道提交 Bug 功能后，旧版"新增 Bug"是否多余

### 分析

旧版"新增 Bug"（整体测试页底部的"新增 Bug"按钮）创建的是**纯本地 Bug**，不会出现在禅道中，也无法享受禅道同步、状态跟踪等功能。

有了"新建禅道 Bug"功能后，对于已接入禅道的项目，确实没有必要再单独新建纯本地 Bug。

### 整改建议

两种方案二选一：

**方案 A（推荐）：直接移除本地新增 Bug 入口**  
删除整体测试页的"新增 Bug"按钮及相关逻辑，只保留"新建禅道 Bug"。

**方案 B：条件性展示**  
仅当该大版本没有配置 `zentao_execution_id` 时才显示本地新增 Bug 按钮，否则隐藏。

## 问题 7：提交禅道 Bug 弹窗缺少字段

### 调研结果

通过对禅道 `bug-create-15-1578.json` 接口（Survey Master 项目）进行实际抓取，禅道创建 Bug 表单完整字段如下：

| 字段 | 说明 | 当前弹窗支持情况 |
|------|------|--------------|
| `title` | Bug 标题 | ✅ 已支持 |
| `severity` | 严重程度（1-4） | ✅ 已支持 |
| `pri` | 优先级（1-4） | ✅ 已支持 |
| `steps` | 重现步骤（富文本，有模板：步骤/结果/期望） | ✅ 已支持（但为纯文本） |
| `assignedTo` | 指派给 | ✅ 已支持（但因问题5用户为空） |
| `type` | Bug 类型（codeerror/config/install/security等） | ❌ 缺失 |
| `moduleID` | 所属模块（树形结构，如"移动端web/设备绑定"） | ❌ 缺失 |
| `openedBuild` | 影响版本（build 下拉选择） | ❌ 缺失 |
| `storyID` | 关联需求（从产品 story 列表选择） | ❌ 缺失 |
| `os` | 操作系统 | ❌ 缺失 |
| `browser` | 浏览器 | ❌ 缺失 |
| `deadline` | 截止日期 | ❌ 缺失 |
| `keywords` | 关键字 | ❌ 缺失 |
| `mailto` | 抄送人 | ❌ 缺失 |

### 整改建议（优先级排序）

**高优先级（影响核心使用）：**
1. **所属模块（moduleID）**：禅道默认分模块管理 Bug，不填会使 Bug 归属混乱。需要在 create-meta 接口中一并返回 `modules` 树，弹窗里增加一个下拉。
2. **影响版本（openedBuild）**：记录 Bug 在哪个 build 中发现，是 Bug 管理基本信息。当前 build 列表已经可以从 meta 获取，只需补充表单项。
3. **修复 指派人不显示问题**（见问题5）。

**中优先级：**
4. **Bug 类型（type）**：禅道默认有"代码错误/配置相关/安装部署/安全相关"等选项，建议补充下拉选择，默认"codeerror"。
5. **关联需求（storyID）**：可从 meta 的 `stories` 列表中选择，但非必填项。

**低优先级（可选）：**
6. 操作系统、浏览器（对移动端项目意义不大）
7. 截止日期、关键字、抄送人

### 注意事项

- 当前的 `steps` 字段为纯文本，而禅道期望 HTML 格式（带 `<p>` 标签的模板：`[步骤]</p><p></p><p>[结果]</p><p></p><p>[期望]</p>`）。提交时需将纯文本转换为 HTML 格式，否则在禅道端显示格式较差。

## 问题 8：整体测试页 Bug 无法点击展开

### 调研结论

整体测试页的 Bug 列表**从未设计过点击展开/折叠功能**。每条 Bug 目前是一个**固定展开的 `<tr>` 行**，所有内容（标题、徽标、操作按钮、验证列）始终全部可见，没有折叠态。

代码结构（`stage5.js` `buildS5RowHtml` 函数）：
```html
<tr class="stage5-row-card" data-bug-id="...">
  <td>Bug编号</td>
  <td>Bug标题 + 徽标行</td>
  <td>操作（编辑/删除/指派）</td>
  <td>验证操作（勾选+下拉+保存按钮）</td>
</tr>
```

没有任何 `onclick` 展开逻辑、没有 `<details>/<summary>` 包裹、没有隐藏行。

### 现存问题

当 Bug 数量较多时，每条 Bug 占据较大高度，页面内容密度高，用户需要大量滚动；且部分信息（如禅道备注 `closeCommentHtml`）即便内容较长也一直展示，无法收起。

### 整改建议

将每条 Bug 改为**可折叠卡片**模式：

- **折叠态**：只显示 Bug 编号、标题、禅道状态徽标、操作链接
- **展开态**：在折叠态基础上，额外显示同步信息徽标、关闭备注、其他人闭环情况（`other_records`）、闭环确认区域（勾选框 + 备注 + 保存按钮）

**实现方式（推荐）：**  
将 `<tr>` 拆为两行：
1. 摘要行（`<tr class="s5-summary-row">`）：点击切换第二行的显示/隐藏
2. 详情行（`<tr class="s5-detail-row" style="display:none">`）：验证操作区域

或者将整个列表从 `<table>` 改为卡片式 `<div>` 布局，配合 `<details><summary>` 原生折叠（体验更佳）。

**优先级：P2（体验改善，非功能缺陷）**
