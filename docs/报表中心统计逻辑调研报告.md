# 报表中心统计逻辑调研报告

> 背景：Bug 数据改为以禅道为主数据源后，报表中心多处指标失真。本报告梳理各项指标的统计口径、定位不准的根因，并给出修改建议。仅做调研，不改动代码。
>
> 作者：调研整理 · 2026-04-24

---

## 0. 数据源与关键字段

### 0.1 Bug 数据进入本地表的三条路径

| 路径 | 触发 | 本地 Bug 字段写入情况 |
|---|---|---|
| **A. 浏览器扩展同步**（`app/services/zentao_sync_service.py::_apply_bug`） | 操作员在禅道 Web 页面创建/修改 Bug，扩展推 payload 到 `/api/zentao_sync/` | 写入 `created_at=local_now()`、`created_by_id=_resolve_actor_for_apply`（按 `creatorName` 匹配本地用户，找不到**兜底为 admin**）、`source_type` 根据 route decision 落为 CASE/REQUIREMENT/RETEST/MANUAL；**不写 `closed`、`fixed_minor_version_id`、`dispatched_to_id`** |
| **B. 整体测试页"全量同步"**（`app/services/overall_test_service.py::sync_zentao_major_bugs`） | 页面点击按大版本拉取禅道 bug 列表 | 新建行时 `source_type=MANUAL`、`created_by_id=current_user.id`（当前登录测试人员）、`created_at=local_now()`；若 `zentao_live_status == "closed"` 会把 `closed=True` 并尝试补一条 `BugStage5Record(source="zentao_sync")`；**仅当禅道 closedBy.account 能匹配到 `UserZentaoBinding`**，否则不计入 Stage5；**不写 `dispatched_to_id`、`fixed_minor_version_id`** |
| **C. 单条禅道动作**（`app/api/routes/zentao_bug_actions.py`） | 点击"关闭/激活/指派/删除"按钮 | `close_bug`→仅更新 `zentao_live_status="closed"`（**不改 `closed` 字段**）；`active_bug`→显式把 `closed=False`；`delete_bug`→`zentao_deleted=True` |

### 0.2 被报表使用的关键字段与来源

| 字段 | 含义 | 谁写入 |
|---|---|---|
| `BugTracking.created_at` | 本地插入时刻 | 所有路径均 `local_now()`，**不是禅道实际提交时间** |
| `BugTracking.updated_at` | 本地任意字段变更时间；每次全量同步 upsert 都会刷新 | ORM 自动 + 手动 `= local_now()` |
| `BugTracking.closed` | 语义混合："本地已闭环"或"禅道已关闭" | Stage5 提交 / overall_test 全量同步（zentao=closed 时）/ zentao_bug_actions reactivate；**zentao_bug_actions close 不会设置** |
| `BugTracking.closed_by_id` | 本地闭环者 | Stage5 提交；reactivate 清空 |
| `BugTracking.dispatched_to_id` | 指派给谁 | 仅 Stage5 "分派"流程/老 legacy bug 手工填；**禅道同步路径从不填** |
| `BugTracking.fixed_minor_version_id` | 开发修复版本 | 仅 Stage5 `submit_result` 写入；**禅道同步路径从不填** |
| `BugTracking.source_type` | 来源枚举 | 浏览器扩展按 route decision 推；整体测试全量同步统一落 MANUAL |
| `BugTracking.zentao_live_status` | 禅道侧实时状态（active/resolved/closed） | 浏览器 hydrate / 整体测试同步 / 单条 close/active |
| `BugTracking.zentao_deleted` | 禅道是否被软删 | 单条 delete 路径 |
| `BugTracking.zentao_assigned_to_account/name` | 禅道真实指派人 | 整体测试同步时写入 |
| `BugStage5Record.test_done` | 本地 Stage5 确认已验证 | 用户在整体测试页勾选 / 禅道同步 auto create |

## 1. 各接口统计规则逐项分析

### 1.1 `GET /reports/summary`（总览 + 趋势 + 团队对比 + Bug 来源饼图）

| 指标 | 口径 | 依赖字段 |
|---|---|---|
| `executed_requirements` | 时间段内 `TestExecution.executed_at` 落在范围内、按 `requirement_id` 去重计数 | `TestExecution` |
| `created_cases` | 时间段内创建的本地 TestCase，排除"关联版本复制"产生的需求（audit: `requirement.link_major`） | `TestCase.created_at` |
| `created_bugs` | 时间段内 `BugTracking.created_at` 落在范围内的行数 | **`BugTracking.created_at`** |
| `retested_reqs` | audit log `retest.submit`，同需求 passed 变化计一次 | `AuditLog` |
| `closed_bugs` | 时间段内 `BugStage5Record.updated_at` 落在范围内、`test_done=True` 且 `newly_found_bug_id is null`，按 `bug_tracking_id` 去重 | `BugStage5Record` |
| `created_feedbacks` / `processed_feedbacks` | 反馈处理状态流转 | `FeedbackRecord` + audit |
| 趋势 `trend` | 按天重复跑上述查询 | 同上 |
| 团队对比 `team_comparison` | 只统计 `User.is_team_member=True` 的用户，按 uid 分别跑指标 | — |
| Bug 来源饼图 `bug_source_dist` | 时间段内 `BugTracking.created_at` 落在范围、按 `source_type` 分组计数 | — |

### 1.2 `GET /reports/advanced`

| 指标 | 口径 |
|---|---|
| `top_reqs` | 时间段内创建 Bug 数最多的 7 个需求（按 `BugTracking.created_at` 筛选、`requirement_id` 聚合） |
| `leakage.retest` | `source_type = RETEST` 的 bug 数 |
| `leakage.normal` | `source_type in (CASE, MANUAL)` 的 bug 数 |
| `funnel.total` | 时间段内所有 bug |
| `funnel.fixed` | **`fixed_minor_version_id is not null`** 的数量 |
| `funnel.closed` | **`closed = True`** 的数量 |
| `executions` | 时间段内 `TestExecution` 按 `result_status` 分组计数 |

### 1.3 `GET /reports/version-bugs`

按小版本 `Version` 遍历，统计 `BugTracking.found_minor_version_id == 小版本id` 的数量。

### 1.4 `GET /reports/governance`

| 指标 | 口径 |
|---|---|
| `overdue_requirements` | 未 `retest_done` 且 `created_at <= now - 14d` |
| `overdue_feedbacks` | 非终态 + 创建>7d |
| `unassigned_bugs` | **`dispatched_to_id is None` 且 `closed=False`** |
| `overdue_bugs` | `closed=False` 且 `created_at <= now - 7d` |
| `stale_bugs` | `closed=False` 且 `updated_at <= now - 14d` |
| `assigned_no_progress_bugs` | `dispatched_to_id is not None` 且 `closed=False` 且 `updated_at <= now - 7d` |
| `top_bug_reqs` / `top_feedback_reqs` | 按需求聚合 bug/feedback 数 |
| `close_aging`（Bug/需求/反馈分别有） | 闭环耗时 = `updated_at - created_at`，按天分桶 |
| `feedback_to_bug_ratio` | 关联过 Bug 的反馈 / 反馈总数 |

### 1.5 `GET /reports/zentao-sync-stats`

健康度统计：过时同步、禅道已关但本地未闭环、本地闭环但禅道未关、禅道被软删。此接口本身口径是合理的。

## 2. 明显不准确的点（按严重度排序）

### 🔴 P0. 所有"Bug 时间范围"统计使用的是本地同步时间，而非禅道真实提交时间

**位置**：`summary.created_bugs`、`summary.trend.day_bug`、`bug_source_dist`、`advanced.top_reqs`、`advanced.leakage`、`advanced.funnel.total`、`governance.overdue_bugs`、`governance.close_aging`、所有 `age_days / stale_days` 计算。

**根因**：所有入库路径都用 `local_now()` 作为 `BugTracking.created_at`。`BugTracking` 没有单独存储"禅道侧原始 openedDate"。

**实际影响**：
- 用户昨天一次性全量同步了某个大版本，历史一年内的 bug 会被全部记成"昨天新建"，于是"本月新建 Bug 数"会呈现异常尖峰。
- 按日趋势图完全不能反映真实创建节奏。
- 超期 Bug、长期未更新 Bug 被系统性低估：禅道真实已经挂了三个月的 bug，本地 `created_at` 是昨天 → `age_days=0`，治理 KPI 无法告警。
- `close_aging`（闭环耗时分桶）会把 "同步当天就发现已关闭"的 bug 记成 0 天，均值严重偏低。

---

### 🔴 P1. "创建人"归属严重失真，团队对比完全不可信

**位置**：`summary.overview.created_bugs`、`summary.team_comparison[*].created_bugs`。

**根因**：
- 浏览器扩展路径：`_resolve_actor_for_apply` 按 `draft.creatorName` 在本地 `User.display_name / username` 里查找，**查不到则回落到第一个 admin**。禅道端的 bug 提交者经常是禅道账号名（拼音/英文），和本地 `display_name`（中文）不一致。
- 整体测试全量同步路径：`created_by_id = current_user.id`（即点击同步按钮的测试员自己），**完全与禅道 creator 无关**。
- `team_comparison` 只遍历 `is_team_member=True` 的用户，禅道里非团队成员创建的 bug 不会出现在对比中，但 `overview.created_bugs` 的计数又限定为 team_ids，两者会对不上。

**实际影响**：
- "admin 创建了 300 个 bug，其他人 0 个"——admin 被动背锅。
- 点同步按钮的那个人，他的"创建 Bug 数"会被虚增为整个版本的同步总量。
- 按成员工作量考核完全失真。

---

### 🔴 P2. `funnel.fixed`（开发处理完毕）在禅道接入模式下基本永远是 0

**位置**：`advanced.funnel.fixed`（前端展示为"开发处理完毕"）。

**根因**：判定依据是 `fixed_minor_version_id is not null`，该字段**仅由 Stage5 的 `submit_result` 本地提交写入**。禅道同步既不写，禅道中"已解决（resolved）"状态也没被识别为 fixed。

**实际影响**：漏斗图中间一级常年为 0 或远小于 total，"开发解决率"完全误导。

---

### 🔴 P3. 治理板"无人处理 Bug" 几乎对所有禅道 bug 都误报

**位置**：`governance.kpis.unassigned_bugs`、`governance.bugs.unassigned_list`。

**根因**：判定 `dispatched_to_id is None`，但**禅道同步从不写本地 `dispatched_to_id`**。禅道真实指派人在 `zentao_assigned_to_account / zentao_assigned_to_name` 里，报表没用到。

**实际影响**：
- 治理页"无人处理 Bug"约等于"禅道里的 bug 总数 - 本地闭环过的"，告警失效。
- 同理 `assigned_no_progress_bugs` 永远是 0（永远不会"已指派"）。

---

### 🟠 P4. `closed` 字段语义割裂 → `closed_bugs` / `funnel.closed` 不一致

**位置**：`summary.overview.closed_bugs`、`advanced.funnel.closed`、`governance` 各种 `not closed` 过滤。

**具体问题**：
- `summary.overview.closed_bugs` 用的是 **`BugStage5Record.test_done=True`** —— 本地 Stage5 口径。
- `advanced.funnel.closed` 用的是 **`BugTracking.closed=True`** —— 混合口径：
  - 本地 Stage5 提交会设置 True
  - `overall_test` 全量同步发现 `zentao_live_status=closed` 也设置 True
  - 但 `zentao_bug_actions.close_bug`（单条关闭）**不设置 True**
  - `reactivate` 强制设回 False，可能覆盖 Stage5 本地闭环状态
- `governance` 全部 KPI 基于 `closed=False` 判定，同样受混合口径影响。

**实际影响**：同一个"已关闭 Bug"，在 summary 里看是 A 个，在 advanced 漏斗里看是 B 个，数字对不上。

---

### 🟠 P5. "Bug 来源分布"饼图在禅道接入后失真

**位置**：`bug_source_dist`、`advanced.leakage`。

**根因**：
- 整体测试"全量同步"创建的行一律落 `BugSourceType.MANUAL`，即使该 bug 在禅道里明显挂在某个需求下。
- 扩展同步路径虽然有 route decision 区分 CASE/REQUIREMENT/RETEST/MANUAL，但决策受浏览器事件的上下文影响，非幂等稳定。
- `advanced.leakage.normal` = `CASE + MANUAL`，分母会被 MANUAL 稀释，导致"漏测率"看起来很低。

**实际影响**：来源饼图几乎被"手工"垄断，失去了区分度；漏测占比偏低。

---

### 🟠 P6. 被禅道软删的 Bug 仍进入业务统计

**位置**：`summary`、`advanced`、`governance` 的所有 bug 查询。

**根因**：只有 `zentao_sync_stats` 显式过滤 `zentao_deleted != True`，其他接口都没有过滤。

**实际影响**：在禅道被删的 bug 仍计入总数、超期、未闭环等，而前端"整体测试"列表已经把它隐藏，数据对不上。

---

### 🟡 P7. `found_minor_version_id` 靠 `opened_build_ids` 匹配，经常匹不到

**位置**：`/reports/version-bugs`（按小版本统计）。

**根因**：`_match_minor_by_build_ids` 要求 `Version.zentao_build_id in opened_build_ids`。如果本地版本表未同步对应的 `zentao_build_id`，或禅道 bug 没填 openedBuild，则 `found_minor_version_id = None` → 该 bug 在版本柱状图里消失。

**实际影响**：按版本维度的 Bug 数量偏低，版本对比不公允。

---

### 🟡 P8. `close_aging`（Bug 闭环耗时）的分子分母都用本地时间

**位置**：`governance.bugs.close_aging`。

**根因**：`updated_at - created_at`。`updated_at` 每次同步都会被刷新，`created_at` 又是同步时刻。两者均不反映禅道真实"从提交到关闭"的耗时。

**实际影响**：闭环耗时均值/中位数都趋近于 0，失去参考价值。

---

### 🟡 P9. `closed_bugs` 若禅道关闭人未绑定 `UserZentaoBinding`，会彻底漏统

**位置**：`summary.overview.closed_bugs`（依赖 Stage5 记录）。

**根因**：`_auto_create_zentao_close_record` 需要 `UserZentaoBinding.zentao_account == closed_by_account`，否则不创建 Stage5 记录。

**实际影响**：禅道里非本地注册用户关闭的 bug（比如外包、PM、离职账号），不会出现在"关闭 Bug 数"中。

---

### 🟡 P10. 单条 `zentao_bug_actions.close_bug` 关闭不会联动 `closed` 和 Stage5

**位置**：整体测试页的"关闭"按钮走 `close_bug` 路径。

**根因**：只更新 `zentao_live_status="closed"`；不设置 `closed=True`；不写 Stage5。

**实际影响**：用户以为在 OmniQA 点了关闭，报表里就能反映，但实际上 `closed_bugs` 数不会增加，funnel.closed 也不会加，需要再做一次"整体测试全量同步"才能对齐。这和 P4 是同一根因的不同切面。

---

## 3. 修改建议（按投入产出排序）

### 3.1 建议 1：补一个 `zentao_opened_at` 字段，用真实禅道时间做所有时间统计 ⭐⭐⭐

**改动点**：
1. `BugTracking` 新增 `zentao_opened_at: DateTime | None`。
2. 在 `_normalize_zentao_bug_summary`、浏览器扩展 `_apply_bug` 里解析 `bug.openedDate` 存入；本地直接新建的 bug 沿用 `created_at`。
3. `report_service` 所有用 `BugTracking.created_at` 做时间范围过滤和 age 计算的地方，改为 **`COALESCE(zentao_opened_at, created_at)`**。
4. `governance` 里 `age_days` 的分子同样换成 `COALESCE(zentao_opened_at, created_at)`。

**收益**：一次性解决 P0、P8 两个严重问题，时间维度指标全部回归真实语义。

---

### 3.2 建议 2：统一 `closed` 语义，引入清晰分层 ⭐⭐⭐

**建议定义**：
- `closed` 保留为"本地 Stage5 闭环"语义（与 Stage5 绑定，由本地测试人员确认）。
- 新增 `zentao_closed: bool`（或直接用 `zentao_live_status=="closed"` 的现成字段）表示"禅道侧已关闭"。
- 报表指标语义改为：
  - `funnel.total` = 全部 bug（含禅道删除前）
  - `funnel.resolved` = `zentao_live_status in ("resolved","closed")`（开发完成）
  - `funnel.closed` = 禅道已关闭（`zentao_live_status=="closed"`）
  - `funnel.verified` = 本地 Stage5 闭环（`closed=True`）
- 治理页 `unassigned / overdue / stale` 的 "未关闭" 过滤统一改为 `zentao_live_status != "closed" AND closed = False`（双保险）。

**收益**：解决 P2、P4、P10；漏斗图从三级变四级，更贴近真实流程。

---

### 3.3 建议 3：`dispatched_to_id` 在禅道同步时联动写入 ⭐⭐

**改动点**：在 `_upsert_zentao_bug_summary`、`_apply_bug` 里，拿到 `assigned_to_account` 后：
- 查 `UserZentaoBinding` 找到对应的 `user_id` → 回填到 `dispatched_to_id`。
- 治理页 `unassigned_bugs` 判定改成 `dispatched_to_id IS NULL AND zentao_assigned_to_account IS NULL`（两边都没指派人才算无人处理）。

**收益**：解决 P3，治理板的"无人处理"和"已指派未处理"回到正确语义。

---

### 3.4 建议 4：所有 Bug 查询默认过滤 `zentao_deleted=False` ⭐⭐

**改动点**：在 `report_service` 顶部封装一个通用过滤函数：

```python
def _active_bugs(query):
    return query.filter(or_(BugTracking.zentao_deleted.is_(False), BugTracking.zentao_deleted.is_(None)))
```

summary / advanced / governance 的 bug 基础查询统一套一层。若业务上需要"含已删"视图，可以加 `include_deleted=True` 开关。

**收益**：解决 P6。

---

### 3.5 建议 5：修正 `created_by_id` 归属 ⭐⭐

**改动点**：
- 整体测试全量同步路径：`created_by_id` 应**优先按禅道 `openedBy` 账号映射到本地 user**（通过 `UserZentaoBinding`），映射不到再兜底为 `current_user.id`。顺手给新建 bug 存一份 `zentao_opened_by_account / name`。
- 浏览器扩展路径：`_resolve_actor_for_apply` 兜底到 admin 的行为改成兜底到"系统账号"（专门建一个 `zentao_sync_bot` 用户），避免污染 admin 的个人报表。
- `team_comparison` 补一行"未匹配成员"，显示未绑定禅道账号的创建量。

**收益**：解决 P1，团队对比恢复可信度。

---

### 3.6 建议 6：区分"来源"是在禅道侧还是本地侧 ⭐

**改动点**：整体测试全量同步路径，当 bug 在禅道有 `storyId / requirement` 时，`source_type` 应推断为 `REQUIREMENT` 而非统一 MANUAL。更进一步，可以根据 `zentao_source_type` 字段细化。

**收益**：解决 P5，来源饼图和 leakage 重新具有区分度。

---

### 3.7 建议 7：同步禅道 `zentao_build_id` 时保证覆盖率 ⭐

**改动点**：检查 `version_service` 是否在拉取小版本时一并写入 `zentao_build_id`。如果有缺失，补一个一次性回填脚本或在 `_upsert_zentao_bug_summary` 里加一个按 version_no 模糊匹配的兜底。

**收益**：解决 P7。

---

### 3.8 建议 8：禅道单条关闭 / 激活与 Stage5 记录联动 ⭐

**改动点**：`zentao_bug_actions.close_bug` 成功后，除 `zentao_live_status="closed"` 外：
- 设置 `BugTracking.closed = True`（若 Stage5 闭环和禅道关闭被统一）。
- 调用 `_auto_create_zentao_close_record`（把现在的 overall_test 内部方法提到 bug_service 里复用）补一条 Stage5 记录，归属到当前 `current_user`。

或者在 P2 采用"分层口径"后，单条关闭只需更新 `zentao_live_status`，`closed_bugs` 的 KPI 改用 `zentao_live_status=="closed"` 统计即可，不再需要联动。

**收益**：解决 P10、P9 中一部分。

---

### 3.9 建议 9：在前端每个指标卡旁展示一句话口径说明 ⭐

## 5. 验收要点（实施后用于自验）

1. 挑一个禅道上存在 1 年历史的大版本，第一次同步后：
   - "本月新建 Bug 数"应只计入 openedDate 在本月内的 bug（而不是全 1 年的 bug）。
   - 治理页"超期 Bug" 应立刻能看到真实 1 年前的 bug。
2. 用 admin 以外的账号点全量同步，admin 的"创建 Bug 数"不应变化。
3. 找一条禅道已指派给 A 的 bug，治理页"无人处理" 不应出现该 bug；"已指派未处理" 应能展示。
4. 在禅道端删除一条 bug，下一次同步后报表 KPI 中 bug 总数应减 1。
5. 漏斗图 total ≥ resolved ≥ closed ≥ verified，且四者差值能从具体 bug 列表对应上。
