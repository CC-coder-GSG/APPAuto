# 禅道全量 Bug 入库方案

> 调研日期：2026-04-24  
> 调研范围：当前测试管理系统代码、当前本地数据库、你提供的禅道账号可访问数据  
> 目标：评估“把禅道上的全部 Bug 获取并保存到数据库中”是否可行，以及应该怎么做

## 1. 结论先说

可以做，而且成本没有你担心的那么高，但前提是 **不要直接把禅道全量 Bug 塞进现有 `bug_tracking` 表**。

更合理的做法是：

1. 新建一套 **禅道 Bug 镜像表**，专门保存禅道原始 Bug 数据。
2. 现有 `bug_tracking` 继续只承载“测试管理系统业务 Bug”。
3. 全量同步按 **产品维度** 拉取 `products/{product_id}/bugs`，先做摘要镜像，不要一开始就逐条拉详情/动作历史。
4. 同步策略采用：
   - 首次全量
   - 日常增量
   - 每天一次全量校准

这样能同时解决两个问题：

- 你可以拿到禅道上的全部 Bug 并入库。
- 不会破坏当前系统里“按版本、按整体测试、按 Stage5 闭环”的现有业务语义。

## 3. 真正的难点不在“拉取”，而在“落库”

### 3.1 为什么不能直接把全部禅道 Bug 塞进 `bug_tracking`

[app/models/bug.py](/E:/APPAUTO/APPAuto/app/models/bug.py:14) 里的 `BugTracking` 是一个明显的业务表，不是纯镜像表。

它有这些特点：

- `major_version_id` 必填
- `source_type` 必填
- 带有 `found_minor_version_id`
- 带有 `fixed_minor_version_id`
- 带有 `test_done`
- 带有 `closed`
- 带有 `closed_by_id`
- 带有 `dispatched_to_id`

这些字段都带有“测试管理系统内部流程语义”，而不是“禅道原始 Bug 语义”。

如果把禅道全库都直接写进这个表，会出现几个问题：

1. 很多禅道 Bug 根本不属于当前任何一个大版本，但 `major_version_id` 又不能为空。
2. `source_type` 会被迫乱填，导致报表口径进一步失真。
3. `closed/test_done/fixed_minor_version_id` 会和禅道状态、Stage5 状态混在一起。
4. 当前系统里很多功能默认把 `bug_tracking` 当作“业务处理中 Bug”，全量导入会污染现有页面和报表。

结论：**`bug_tracking` 只能继续做业务表，不能兼做禅道全量镜像表。**

## 4. 推荐方案

## 4.1 表设计建议

建议新增两张表。

### A. `zentao_bug_mirror`

用途：保存禅道 Bug 的摘要镜像。

建议字段：

- `zentao_bug_id`，唯一
- `product_id`
- `product_name`
- `project_id`
- `execution_id`
- `story_id`
- `title`
- `status`
- `severity`
- `pri`
- `type`
- `resolution`
- `opened_by`
- `opened_date`
- `assigned_to`
- `assigned_date`
- `resolved_by`
- `resolved_date`
- `closed_by`
- `closed_date`
- `last_edited_by`
- `last_edited_date`
- `opened_build`
- `steps`
- `deleted`
- `raw_json`
- `first_synced_at`
- `last_synced_at`

### B. `zentao_product_sync_state`

用途：保存每个产品的同步游标和状态。

建议字段：

- `product_id`，唯一
- `product_name`
- `last_full_sync_at`
- `last_incremental_sync_at`
- `last_seen_bug_id`
- `last_seen_edited_at`
- `last_sync_status`
- `last_error_message`

## 4.2 同步策略建议

### 第一阶段：首次全量同步

流程：

1. 先拉 `GET /api.php/v1/products`
2. 对每个产品拉 `GET /api.php/v1/products/{product_id}/bugs?limit=100&page=n`
3. 逐页 upsert 到 `zentao_bug_mirror`
4. 每页成功后更新该产品的同步状态

这里建议：

- 并发数控制在 `4 ~ 6`
- 每页 `limit=100`
- 只存列表页已有字段，不做逐条详情补抓

原因很简单：

- 我实测列表页已经带了很多关键字段：`title/status/openedDate/assignedTo/closedBy/closedDate/lastEditedDate/steps`
- 这已经足够支撑“全量入库、搜索、统计、状态对账”
- 如果一开始就对每个 Bug 再打一次详情接口，成本会立刻放大一个数量级

### 第二阶段：日常增量同步

不要每 5 分钟全量扫全库，建议这样做：

1. 高频增量：每 10 分钟扫一次“最近活跃产品”
2. 低频校准：每天凌晨做一次全量校准

高频增量的两种实现思路：

#### 方案 A：按最近页扫描

对每个产品只扫前 `N` 页，比如前 `3 ~ 5` 页，按最新顺序抓。

适合场景：

- 最近新增/最近变更的 Bug 会集中在前几页
- 禅道接口没有特别稳定的 `updated_after` 过滤参数时，这种方式最稳

#### 方案 B：按时间水位提前停止

如果实测确认 `orderBy=editedDate_desc` 稳定生效，可以：

1. 按 `lastEditedDate` 倒序拉
2. 当整页都早于上次同步时间时提前停止

这个方案更省，但前提是你们当前这套禅道版本对排序参数支持稳定。

我的建议是：

- 第一版先上 **方案 A**
- 等线上观察稳定后，再考虑切换到方案 B

### 第三阶段：每天一次全量校准

这个动作必须保留，因为增量策略无法 100% 覆盖这些场景：

- 老 Bug 被重新激活
- 老 Bug 被关闭
- 老 Bug 被删除
- 某些产品之前是 0 条 Bug，后来新增了 Bug

全量校准的意义不是追求高频，而是保证最终一致性。

---

## 4.3 如果未来真到 1 万条，成本大概多高

按照我这次实测的接口体积和请求模式，粗略估算：

- 1 页 100 条 Bug
- 10000 条大概是 100 页数据
- 再加上产品枚举，请求量仍然是“百级别”，不是“万级别”

所以真正高成本的情况只有两种：

1. 你对每条 Bug 都再去单独拉详情、评论、动作历史
2. 你把禅道全库直接写进当前业务表，导致后续查询和页面都被拖慢

只要坚持“**摘要镜像表 + 增量同步 + 夜间全量校准**”，`10000` 条这个量级完全可以接受。

---

## 5. 我建议的落地顺序

### 第 1 步

先做一套独立的 `zentao_bug_mirror` 表，不碰当前 `bug_tracking` 业务逻辑。

### 第 2 步

先实现“产品维度全量抓取 + 入镜像表”，只存摘要字段。

### 第 3 步

补上一个同步状态表 `zentao_product_sync_state`，支持断点续跑和错误追踪。

### 第 4 步

再做高频增量同步和夜间全量校准。

### 第 5 步

最后再考虑把这张镜像表用于：

- 禅道全库搜索
- 禅道状态统计
- 禅道与本地业务 Bug 对账

而不是一开始就替换现有整体测试和报表逻辑。

---

## 6. 最终建议

我的明确建议是：

- **要做全量入库**
- **但不要写进现有 `bug_tracking`**
- **先做“禅道全量镜像层”**

原因是：

1. 当前可见总量并不大，2026-04-24 实测只有 `315` 条，完全值得做。
2. 即便以后涨到 `10000` 条，只做列表摘要镜像，成本仍然可控。
3. 当前系统的最大风险不是接口慢，而是“把禅道全量数据污染到现有业务表里”。

如果你后续要我继续推进，下一步最合理的工作不是直接改代码，而是先把这套镜像表结构和同步任务边界再细化成一份实施清单。
