# 报表中心修复 + 禅道全量同步改进方案

> 统一解决三件事：
> 1. 报表中心从禅道数据接入后多项指标失真
> 2. "全部版本"视图当前无法触发同步
> 3. 需要把禅道上**全部** Bug（~5000 条）定期入库
>
> 日期：2026-04-24 · 范围：全量改造

---

## 0. 背景数据（用 chenwenbo 账号实测）

| 指标 | 值 |
|---|---|
| 禅道产品数 | 62 |
| 有 bug 的产品数 | 16 |
| **禅道 Bug 总数（含已关闭/已删）** | **5197** |
| 最大产品 bug 数 | Survey Master (id=15)：**4872** |
| 次大：WoSense App (id=310) | 127 |
| 次大：M300 Pro 系列 (id=145) | 74 |
| 单条 bug payload 大小 | ~2.5 KB |
| 全量 5000 条 payload | ~12 MB |
| 单次 `/products/{id}/bugs?limit=500&status=all` | ~1.3 秒 |
| 并发 8 线程扫 62 个产品元数据 | 8.2 秒 |
| Survey Master 4872 条串行分页拉完 | 13.6 秒 |

结论：**全量同步完全可行**。8~10 线程并发、分页 limit=500，总耗时 15~30 秒落库可期。

**关键发现**：禅道 `/products/{id}/bugs` **默认只返回未关闭的 bug**（186 条），必须加 `status=all` 才能拿到真实全量（4872 条）。这条之前代码里没显式传 `status=all`，意味着现在整体测试的单版本同步也只同步了"未关闭"的那部分，这本身就是一个隐性 bug。

## 1. 报表中心核心问题回顾

> 详细见 `报表中心统计逻辑调研报告.md`，此处列要点与本方案要做的修复绑定。

| ID | 问题 | 影响面 | 本次修复位置 |
|---|---|---|---|
| P0 | 所有 bug 时间统计用本地同步时间，非禅道真实 openedDate | summary/advanced/governance 时间类指标全部失真 | **第 2 阶段** |
| P1 | `created_by_id` 被打给"点同步按钮的人"或 admin 兜底 | 团队对比指标扭曲 | **第 2 阶段** |
| P2 | `funnel.fixed` 仅靠本地 Stage5 写入，禅道接入后永远为 0 | 漏斗图中间级失效 | **第 3 阶段** |
| P3 | `dispatched_to_id` 同步路径不写 | "无人处理 Bug"几乎全是误报 | **第 2 阶段** |
| P4 | `closed` 语义割裂（Stage5 / 全量同步 / 单条关闭 三路不一致） | summary 和 advanced 对不上 | **第 3 阶段** |
| P5 | 来源分布饼图被 MANUAL 稀释 | leakage 漏测率偏低 | **第 2 阶段** |
| P6 | `zentao_deleted=True` 的 bug 仍进入统计 | KPI 虚高 | **第 2 阶段** |
| P7 | `found_minor_version_id` 匹配依赖 `zentao_build_id` | 版本柱图漏计 | **第 2 阶段** |
| P8 | `close_aging` 耗时基于本地时间 | 闭环耗时失去参考 | **第 3 阶段** |
| P9 | 禅道关闭人未绑定则 Stage5 记录不创建 | `closed_bugs` 漏统 | **第 3 阶段** |
| P10 | 单条 close_bug 不联动 `closed` 字段 | 需触发一次全量同步才对齐 | **第 3 阶段** |

## 3. 数据模型改造（Phase 1）

### 3.1 `BugTracking` 新增字段

```python
# app/models/bug.py
zentao_opened_at:     Mapped[Optional[datetime]]  # 禅道 openedDate（真实提交时间）
zentao_opened_by_account: Mapped[Optional[str]]   # 禅道 openedBy.account
zentao_opened_by_name:    Mapped[Optional[str]]
zentao_resolved_status: Mapped[Optional[str]]  # 可选：'active' / 'resolved' / 'closed'
                                                # 或直接复用已有 zentao_live_status
```

> `zentao_live_status` 已经存在且够用，`zentao_resolved_status` 不重复建，复用 `zentao_live_status`。

### 3.2 Alembic/SQL 迁移

```sql
ALTER TABLE bug_tracking ADD COLUMN zentao_opened_at DATETIME;
ALTER TABLE bug_tracking ADD COLUMN zentao_opened_by_account VARCHAR(100);
ALTER TABLE bug_tracking ADD COLUMN zentao_opened_by_name VARCHAR(100);
CREATE INDEX idx_bug_zentao_opened_at ON bug_tracking(zentao_opened_at);
```

### 3.3 一次性回填脚本

`scripts/backfill_zentao_opened_at.py`：遍历所有 `zentao_bug_id IS NOT NULL` 的 BugTracking，批量调禅道 `/products/{pid}/bugs` 取回 openedDate/openedBy，填入新字段。首次全量同步（Phase 4）完成后这一步其实可省——新同步会自动写入。

## 4. 同步链路改造（Phase 2）

### 4.1 新增 `POST /overall-test/sync-zentao-all`

**入参**：
```json
{"software_id": 1, "force": false}
```

**行为**：
1. 按 `software_id` 找到本地 `SoftwareProduct`，拿到它映射的所有 `zentao_product_id`。
   - 现有映射来源：`BugTracking.zentao_product_id` 分组、`Version.zentao_product_id` 分组、或在 `SoftwareProduct` 上新增一个 `zentao_product_ids` 字段显式配置（推荐，减少 guess）。
2. 并发（`ThreadPoolExecutor(max_workers=8)`）调 `/products/{pid}/bugs?limit=500&status=all&page=N`，分页拉完所有 bug。
3. 收集到的 bug list 做一次 DB 批量查询 `BugTracking.zentao_bug_id IN (...)` 建索引字典，避免 N+1。
4. 对每条 bug 执行 upsert：
   - 映射 `major_version_id`：
     1. `opened_build.id` → `Version.zentao_build_id`（MINOR）→ `parent_id` 推出 MAJOR
     2. `execution.id` → `Version.zentao_execution_id`（MAJOR）
     3. `product.id` + `affectedVersion` 模糊匹配本地大版本号
     4. 都失败 → 挂到软件的"未归类大版本"桶（新建一个 dummy major，如 `V0.0.0-unclassified`，每个 software 一个），**保证 bug 不丢**
   - 映射 `found_minor_version_id`：复用现有 `_match_minor_by_build_ids`
   - 映射 `created_by_id`：按 `openedBy.account` 查 `UserZentaoBinding`，找到→本地 user.id；找不到→**系统用户 `zentao_sync_bot`**（需预先建一个，不要再兜底到 admin）
   - 映射 `dispatched_to_id`：按 `assignedTo.account` 查 `UserZentaoBinding`，找到→本地 user.id
   - 写入 `zentao_opened_at = openedDate`、`zentao_opened_by_account/name = openedBy.*`
   - 写入 `zentao_deleted = (bug.deleted == "1")`
   - 写入 `zentao_live_status`（active / resolved / closed）
   - 不再用 `created_at = local_now()` 作为业务时间依据（保留，仅作审计）
5. 批量 `db.commit()`：每 500 条 commit 一次，避免单事务过大。
6. 返回：
```json
{
  "software_id": 1,
  "zentao_products": [15, 310, 145],
  "remote_total": 5073,
  "created": 4800,
  "updated": 273,
  "matched_major": 4950,
  "unclassified": 123,
  "elapsed_seconds": 18.4,
  "job_id": "..."
}
```

### 4.2 并发与锁

- 模块级 `_sync_all_in_progress: set[int]`（key 为 software_id），同一 software 只允许一个 job 跑。
- TTL：15 分钟兜底，防死锁。
- 前端重复点击 → 返回 `409 Conflict` + 剩余倒计时。

### 4.3 全量同步缓存

- `_sync_cache` 已有（大版本级别），保留不动。
- 全量同步给 software 级别加独立的 `_sync_all_cache: dict[int, datetime]`，TTL 15 分钟。`force=True` 绕过。

### 4.4 现有"单大版本同步"路径的最小改动

- `/executions/{id}/bugs` 和 `/builds/{id}/bugs` 的调用**必须加 `status=all`**。否则已关闭的 bug 永远拉不回来。
- `_upsert_zentao_bug_summary` 中补上对 `openedDate`、`openedBy`、`deleted` 字段的写入。
- `created_by_id` 按同样的 openedBy 映射规则决定，不再无脑用 `current_user.id`。

### 4.5 浏览器扩展同步路径 (`_apply_bug`) 的修复

- `_resolve_actor_for_apply` 的兜底从 admin 改为 `zentao_sync_bot`。
- `draft` 里若有 `openedDate` / `openedBy`，一并写入新字段。

### 4.6 单条 close_bug 动作的修复

- `zentao_bug_actions.close_bug` 成功后：
  - `zentao_live_status = "closed"`（原有）
  - `BugTracking.closed = True`（新增，或改为只认 `zentao_live_status==closed`，见 Phase 3.2）
  - 调用 `_auto_create_zentao_close_record`（这个方法从 overall_test_service 提到公共 bug_service 里）

## 5. 报表中心修复（Phase 3）

所有修改集中在 `app/services/report_service.py`。

### 5.1 统一的 Bug 时间轴

```python
def _bug_time_column():
    # 优先使用禅道真实提交时间，回落到本地 created_at
    return func.coalesce(BugTracking.zentao_opened_at, BugTracking.created_at)
```

替换掉所有 `BugTracking.created_at >= sdt` 和 `BugTracking.created_at <= edt`。

### 5.2 统一的 "活跃 bug" 过滤

```python
def _exclude_deleted(q):
    return q.filter(or_(
        BugTracking.zentao_deleted.is_(False),
        BugTracking.zentao_deleted.is_(None),
    ))
```

所有 bug 基础查询套一层。报表默认不统计 zentao_deleted=True 的 bug。

### 5.3 "关闭 / 修复 / 闭环" 三级分层

漏斗重构：
- `total` = 时间段内所有 active bug
- `resolved` = `zentao_live_status in ('resolved', 'closed')`（禅道侧开发完成）
- `closed` = `zentao_live_status == 'closed'`（禅道侧关闭）
- `verified` = 本地 `closed == True`（Stage5 闭环）

前端漏斗从 3 级变 4 级：**发现 Bug 总数 → 开发已解决 → 禅道已关闭 → 本地验收闭环**。

`summary.overview.closed_bugs` 统一改为 "本地 Stage5 `test_done=True`" 或 "禅道 `zentao_live_status=='closed'` 且在时间范围内" 二者合并去重（按 bug_tracking_id 去重）。

### 5.4 `unassigned_bugs` / 治理看板修复

```python
# governance 无人处理：本地和禅道侧都未指派才算
(BugTracking.dispatched_to_id.is_(None)) 
& (or_(BugTracking.zentao_assigned_to_account.is_(None), 
       BugTracking.zentao_assigned_to_account == ''))
```

"已指派未处理"的定义改成：本地 `dispatched_to_id` 或 `zentao_assigned_to_account` 有值、且 bug 未 closed、且 `zentao_remote_updated_at` 距今 >= 阈值。

### 5.5 `close_aging` 基于真实时间

```python
# 旧： updated_at - created_at
# 新： zentao_close_date - zentao_opened_at （fallback to updated_at - created_at）
close_dt = bug.zentao_close_date or bug.updated_at
open_dt = bug.zentao_opened_at or bug.created_at
if close_dt and open_dt:
    days = max(0, (close_dt - open_dt).days)
```

### 5.6 "来源分布" 按禅道字段细化

`_apply_bug` 和 `_upsert_zentao_bug_summary` 在决定 `source_type` 时新规则：
- 有 `requirement_id` 或 `bug.story` → `REQUIREMENT`
- 有 `bug.case` 或 `linkedCaseId` → `CASE`
- 来自禅道整体测试、无 story / case → `MANUAL`
- 扩展 payload 标识为 retest → `RETEST`

`leakage.normal` 分母剔除 MANUAL（或单独展示三种），漏测率回归真实。

### 5.7 团队对比补"未归属"一行

`summary.team_comparison` 追加一个 `"user_id": 0, "username": "未归属/未绑定"` 的聚合行，聚合所有未能映射到本地 user 的 bug（即归属到 zentao_sync_bot 的那些）。

## 7. 风险与兜底

| 风险 | 缓解 |
|---|---|
| 5000 条全量同步期间超时（>30s 网关超时） | 后端做**异步任务**：接口立即返回 `job_id`，SSE 推进度；默认前端展示进度条 |
| 禅道单次 API 故障（PHP Fatal Error） | 单产品失败降级：跳过并把失败 product_id 记入 `failed_products` 返回给前端 |
| 本地 DB 大事务卡死 | 分批 commit（每 500 条），且 `PRAGMA journal_mode=WAL` 已是 SQLite 默认推荐 |
| 映射不到 major 的 bug 堆积 | 新建 `V0.0.0-unclassified` dummy major，前端单独一个"未归类"筛选项，运维可手工重映射 |
| 新同步字段的历史数据缺失 | 首次全量同步会把所有历史 bug 的 `zentao_opened_at` 回填（因为 `openedDate` 是 upsert 必写） |
| `zentao_live_status` 与 `closed` 语义冲突遗留 | Phase 3 统一以 `zentao_live_status` 为准；`closed` 字段仅表示本地 Stage5 闭环（前端文案同步改） |
| zentao_sync_bot 用户概念新引入 | `app/db/seed.py` 启动时 `get_or_create`，role=USER, is_team_member=False；团队对比单独一行聚合 |
