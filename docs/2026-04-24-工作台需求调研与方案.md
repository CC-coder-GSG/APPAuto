# 工作台需求调研与方案

> 调研日期：2026-04-24
> 调研范围：`docs/工作台需求.md`、现有工作台/复测/整体测试/禅道同步代码、禅道官方 API 文档

## 1. 需求摘要

根据 `docs/工作台需求.md`，这次需求的核心不是单点 UI 调整，而是希望把测试工作台从“手工登记编号”升级成“以禅道真实数据为基础的自动化工作台”：

1. 需要把禅道测试用例同步到系统中。
2. 需要一个独立的“用例页面/Tab”，展示方式尽量接近禅道。
3. 需求工作台不再要求测试人员在分配后手工填写 Bug 编号、用例编号。
4. 点击“用例完成”“测试完成”时，系统应能自动聚合该需求相关的禅道用例和 Bug。
5. 复测工作台不再手工添加“复测新增 Bug”，而是尽量由系统自动识别、归集、再由测试人员给出复测结论。
6. 方案不要求完全按现有设想实现，重点是结合当前系统实际结构给出更合理的落地方式。

## 2. 当前系统现状

### 2.1 需求工作台当前仍以手工录入为主

从现有前后端代码看，需求工作台仍然是“本地 Requirement + 本地 TestCase/BugTracking”的手工维护模式：

- 前端 `frontend/js/tabs/mine.js`
  - 仍保留“逐个添加用例”
  - 仍保留“添加自由 Bug”
  - 仍保留“给用例添加关联 Bug”
  - 测试完成时只是补一条测试执行记录，并不会自动从禅道拉齐该需求的所有用例/Bug
- 后端 `app/api/routes/requirements.py`
  - `POST /requirements/{req_id}/cases`
  - `PUT /test-cases/{case_id}`
  - `DELETE /test-cases/{case_id}`
  这些接口本质都是围绕“手工维护 requirement 下的 test_cases”
- 后端 `app/services/requirement_service.py`
  - `add_case_to_requirement()`
  - `update_requirement_cases()`
  都是在本地直接写 `test_cases` 表

结论：当前需求工作台并没有“根据禅道真实数据自动建账”的能力。

### 2.2 系统已经有“禅道用例同步”的雏形，但还不是完整方案

现有代码里已经存在 testcase 的同步入口：

- `app/services/zentao_sync_service.py`
  - 浏览器同步事件已经支持 `entity_type = testcase`
  - `_apply_testcase()` 会把同步到的 testcase 写入本地 `TestCase`
- `frontend/js/tabs/zentao-sync.js`
  - 禅道同步中心已经能区分 `bug` / `testcase`
  - testcase 事件支持映射 requirement 再应用

但这套机制目前有两个明显限制：

1. 它依赖浏览器侧事件推送，不是“完整全量/增量同步”。
2. 它落库的目标仍是当前 `test_cases` 表，而这个表不是“禅道用例镜像表”，而是“挂在本地 requirement 下的工作台用例表”。

### 2.3 当前 `TestCase` 数据模型不适合直接做“禅道用例中心”

`app/models/testcase.py` 里的 `TestCase` 结构有这些特点：

- `requirement_id` 是必填
- `zentao_case_id`、`zentao_case_url`、`zentao_case_numeric_id` 是附属字段
- 本质上是一条“某个需求下挂了一个用例”的本地关系记录

这说明它更像：

- 工作台关系表

而不是：

- 禅道 testcase 全量镜像表

如果直接拿当前 `test_cases` 表去承接“禅道所有用例 + 独立用例页面 + 自动归集”，后续会遇到几个问题：

1. 一个禅道用例还没映射到本地 requirement 时，没地方存。
2. 一个用例中心页面需要按产品、模块、需求、状态浏览，但当前表的主维度是 requirement。
3. 后续如果要做全量同步、删除同步、状态更新、执行结果展示，当前表字段不够。

### 2.4 复测工作台当前也是“本地证据手工补齐”

`frontend/js/tabs/retest.js` 和 `app/services/retest_service.py` 的逻辑说明：

- 复测页面会展示：
  - 原测试用例下的 Bug
  - 原测试发现的自由 Bug
  - 复测新增 Bug
- 复测新增 Bug 当前仍靠手工输入 `b#xxxx`
- “通过/打回”判断也依赖本地 `BugTracking.is_retest_failed`、`source_type = RETEST` 等字段

结论：复测工作台也不是实时查禅道，而是基于本地证据集做人机协作。

### 2.5 整体测试、报表、工作台目前都依赖本地库，不适合改成“每次实时查禅道”

`overall-test`、`report`、`mine`、`retest` 这几个模块都围绕本地库构建。  
这意味着如果直接把需求改成“点按钮时临时去禅道现查”，会带来三个问题：

1. 口径不一致：页面 A 看本地，页面 B 看禅道实时，数字会对不上。
2. 性能不稳定：工作台和报表会受禅道接口速度影响。
3. 业务状态难沉淀：当前很多状态是“本地 requirement 生命周期 + 本地执行结论”，并不等于禅道原生状态。

## 3. 禅道官方能力调研

禅道官方接口文档显示，这个需求在接口能力层面是可行的，至少测试用例侧并不存在“拿不到数据”的问题。

### 3.1 登录取 Token

官方文档给出了 token 登录方式：

- `POST /api.php/v2/users/login`
- 请求体：`account`、`password`
- 返回：`token`

来源：禅道官方《获取Token》  
https://www.zentao.net/book/api/2142.html

### 3.2 获取产品测试用例列表

官方文档提供了产品维度的 testcase 列表接口：

- `GET /api.php/v2/products/:productID/testcases`
- 支持 `pageID`
- 支持 `recPerPage`
- 单页上限 `1000`

来源：禅道官方《获取产品测试用例列表》  
https://www.zentao.net/book/api/2203.html

这意味着：

- 用例全量同步可以按产品分页拉取
- 不需要靠浏览器页面抓 DOM
- 成本可控，适合做“首次全量 + 后续增量/校准”

### 3.3 获取测试用例详情

官方文档提供 testcase 详情接口：

- `GET /api.php/v2/testcases/:caseID`

来源：禅道官方《获取测试用例详情》  
https://www.zentao.net/book/api/2206.html

这意味着：

- 列表页可以先拉轻量列表
- 详情页按需补拉
- 不必一次把所有富文本/步骤字段塞到工作台主查询里

## 4. 关键差距

结合当前代码和需求，真正的差距不在“有没有接口”，而在下面四件事：

### 4.1 缺少 testcase 镜像层

当前只有：

- 工作台用例表 `test_cases`

缺少：

- 禅道 testcase 镜像表

没有镜像层，就无法稳定支持：

- 独立用例中心
- 自动按 requirement 聚合用例
- 自动识别复测新增 Bug 所属需求
- 后续报表/追溯

### 4.2 需求工作台里的“用例集合”没有自动生成规则

当前 requirement 和 testcase 的关系主要靠人手工建立。  
如果要去掉手工录入，系统必须明确回答：

- 一个需求的 testcase 集合怎么确定？
- 依据 story 关联，还是 execution 关联，还是人工兜底映射？
- 当禅道用例变更时，本地 requirement 下的用例集合是否自动刷新？

### 4.3 复测工作台里的“证据集合”也没有自动归集规则

当前复测能否打回，依赖：

- 原 Bug 是否勾了 `is_retest_failed`
- 是否手工新增了 `source_type = RETEST` 的 Bug

如果要改成自动化，必须先定义：

- 哪些禅道 Bug 算“该 requirement 的复测证据”？
- 新 Bug 是按 story 归属，按关联用例归属，还是按测试人/版本归属？

### 4.4 当前表结构混用了“业务关系”和“同步镜像”

当前 `test_cases` 既在承载：

- requirement 下的业务关系

又在被 `zentao_sync_service` 当作：

- testcase 同步落库目标

这会导致后续边界越来越乱。  
如果继续沿用，会把“工作台关系表”做成“万能表”，后期维护成本很高。

## 5. 方案选型

### 方案 A：所有工作台操作都实时查禅道

做法：

- 工作台打开时实时查禅道 testcase / bug
- 点击“用例完成”“测试完成”“复测完成”时现场查询禅道数据

优点：

- 理论上数据最新
- 本地少存一层 testcase

缺点：

- 与现有系统架构冲突最大
- 性能和稳定性最差
- 禅道一慢，工作台全慢
- 页面、报表、整体测试、复测的统计口径很容易失真

结论：不推荐。

### 方案 B：继续只靠浏览器同步中心补 testcase

做法：

- 继续沿用现在的浏览器同步事件
- 让测试人员在禅道侧操作时触发 testcase 事件
- 再人工映射 requirement

优点：

- 改动最小

缺点：

- 仍然不是完整 testcase 同步
- 仍然依赖人工映射
- 不能满足“独立用例页面”和“自动归集”目标

结论：只能做补充能力，不能作为主方案。

### 方案 C：新增 testcase 镜像层，工作台全部改为“本地自动聚合”

做法：

1. 新增禅道 testcase 镜像表，只保存禅道真实 testcase 数据。
2. 保留当前 `test_cases` 作为“需求工作台关系表”或逐步弱化它。
3. 需求工作台、复测工作台、用例中心统一读取本地镜像，再按业务规则生成各自视图。

优点：

- 最符合当前系统整体架构
- 口径统一
- 性能可控
- 便于后续报表、追溯、自动归类

缺点：

- 需要补一层数据模型和同步任务
- 前期设计要把“镜像表”和“业务关系表”边界定清楚

结论：推荐方案。

## 6. 推荐方案

## 6.1 总体原则

推荐把未来结构拆成两层：

1. 禅道镜像层  
   保存禅道 testcase / bug / story 的真实同步数据。

2. 工作台业务层  
   保存 requirement 生命周期、测试执行结论、复测结论、人工补充说明等本地业务状态。

这两层不要再混在一个表里。

## 6.2 testcase 侧建议

建议新增一张独立镜像表，例如：

- `zentao_testcase_mirror`

至少应包含：

- `zentao_case_id`
- `product_id / product_name`
- `module_id / module_name`
- `story_id`
- `execution_id`
- `title`
- `pri / type / stage / status`
- `last_runner / last_run_result / last_run_date`
- `bugs_count`
- `precondition`
- `steps_digest` 或详情缓存
- `deleted`
- `last_synced_at`
- `raw_payload`

当前 `test_cases` 表建议保留为：

- “本地 requirement 与 testcase 的业务关联表”

不要直接拿它做全量 testcase 镜像。

## 6.3 testcase 同步策略

推荐同步策略：

1. 首次按产品全量同步
   - 通过 `/products/:productID/testcases`
   - 分页拉取，`recPerPage` 可到 `1000`
2. 日常增量同步
   - 如果当前禅道版本接口能提供更新时间筛选，就按更新时间拉
   - 如果不稳定，就采用“按产品分页全量覆盖 + 更新时间比较”的保守方案
3. 详情按需补拉
   - 列表页展示先读镜像
   - 点进 testcase 详情时再调 `/testcases/:caseID`

这样做的好处是：

- 用例中心够快
- 工作台自动归集够稳
- 禅道接口压力可控

## 6.4 需求工作台改造建议

需求工作台建议从“手工录编号”改成“自动聚合 + 人工确认”。

### 推荐规则

一个 requirement 的 testcase 集合优先按以下顺序生成：

1. testcase 的 `story_id == requirement.zentao_story_id`
2. 如果 story 归属不完整，再结合 execution / product / requirement 映射补充
3. 只有自动规则无法覆盖时，才允许管理员在同步中心做人工映射兜底

工作台上的变化建议是：

- 去掉普通测试人员“逐个新增用例编号”的日常入口
- 去掉普通测试人员“手工填写自由 Bug / 用例 Bug 编号”的主路径
- requirement 卡片直接展示系统自动聚合出的 testcase、关联 Bug、测试要点

### “用例完成”的建议定义

建议保留这个动作，但语义改清楚：

- 它不再表示“我已经手工把用例号填完了”
- 而表示“系统自动识别出的 requirement 用例集合，我已确认无误，可以封板”

### “测试完成”的建议定义

建议仍保留按钮，因为这是业务状态，不是同步状态。  
但点击时不再要求先手工补编号，而是：

1. 系统自动读取该 requirement 当前已归集的 testcase 集合
2. 系统自动读取该 requirement 当前归集到的 Bug 集合
3. 用户只填写测试结论、备注、当前发包版本
4. 本地保存测试执行记录并推进 requirement 状态

换句话说：

- “测试完成”应该是业务确认动作
- 不是“补数据动作”

## 6.5 复测工作台改造建议

复测工作台也建议改成“自动证据归集 + 人工裁决”。

### 推荐规则

一个 requirement 的复测证据集合可由以下部分组成：

1. 原测试阶段该 requirement 下已存在的 Bug
2. 与该 requirement 已归集 testcase 关联的 Bug
3. 测试完成后、新出现且可追溯到该 requirement/story/testcase 的禅道 Bug

复测人员在页面上不再以“新增 b#xxxx”为主，而是：

- 系统先自动列出候选证据
- 复测人员只做：
  - 标记旧 Bug 是否未修好
  - 确认新出现 Bug 是否归属该 requirement
  - 最终提交“通过 / 打回”

### 异常兜底

仍建议保留一个低频兜底入口，但不要放在主操作流里：

- 仅管理员或高级测试可手工补记“遗漏的 testcase / bug 归属”
- 入口放到同步中心或专门的“修正映射”面板

这样既能满足真实业务的异常场景，也不会让主流程重新退化成手工台账。

## 6.6 独立“用例中心”页面建议

建议新增独立 Tab，例如：

- `用例中心`

展示风格可以接近禅道，但底层建议读取本地镜像，不要直接嵌禅道页面。

建议提供的能力：

1. 按软件/产品/模块/需求/状态筛选
2. 列表展示：编号、标题、所属需求、优先级、阶段、最近执行结果、最近执行人、最近执行时间、关联 Bug 数
3. 详情面板展示：前置条件、步骤、预期结果、禅道原链接、最近同步时间
4. 支持跳转到本地 requirement、整体测试、复测工作台

这会比“在工作台里到处塞 testcase”更清晰。

## 7. 建议的实施顺序

为了降低风险，建议按四阶段推进，而不是一把梭。

### 第一阶段：打基础

目标：

- 新增 testcase 镜像表
- 跑通 token 登录和产品 testcase 分页同步
- 完成 testcase 全量入库

交付结果：

- 系统里先有稳定 testcase 数据底座

### 第二阶段：先做“用例中心”

目标：

- 基于镜像表做独立用例中心
- 验证字段完整性、列表性能、详情展示

交付结果：

- 先把 testcase 数据“看得见、查得到”

### 第三阶段：改需求工作台

目标：

- 用自动归集规则替代手工录入用例/Bug
- 保留少量管理员兜底入口

交付结果：

- requirement 工作台真正从手工台账转成自动工作台

### 第四阶段：改复测工作台

目标：

- 自动构建复测证据集合
- 复测人员主要做裁决，不再做编号录入

交付结果：

- 复测流程和需求工作台口径统一

## 8. 风险与注意点

### 8.1 不建议直接复用当前 `test_cases` 做镜像表

这是这次调研里最重要的结论之一。  
如果直接在当前 `test_cases` 表上硬扩展，会把“同步数据”和“业务关系”继续耦合，后面很难收拾。

### 8.2 requirement 与 testcase 的自动归属规则必须先定清

技术上能同步 testcase，不代表系统天然知道它属于哪个 requirement。  
这件事必须先把规则定清，否则工作台会出现“自动归错”的问题。

### 8.3 Bug 自动归属也需要有明确优先级

建议优先级：

1. testcase 关联
2. story 关联
3. requirement 明确映射
4. 人工兜底

不要直接按“谁触发了同步”或“谁当前在页面上操作”去归属。

### 8.4 推荐保留“人工修正”能力，但降级为异常流程

完全去掉人工入口并不现实。  
更合理的做法是：

- 主流程自动化
- 异常场景人工修正
- 修正入口集中放到同步中心/管理入口

## 9. 最终建议

基于当前系统结构，我的建议是：

1. 不要做“工作台每次点按钮都实时查禅道”的方案。
2. 不要继续把 testcase 同步直接落在当前 `test_cases` 表上扩着用。
3. 应该先补一层独立 testcase 镜像表，再做“用例中心”。
4. 需求工作台和复测工作台都改成“自动归集证据 + 人工确认结论”。
5. 手工录入 testcase/Bug 编号应从主流程中退出，只保留为异常兜底。

如果后续继续推进，最合理的下一步不是直接改页面，而是先把下面三件事细化成实施清单：

1. testcase 镜像表字段设计
2. requirement 与 testcase 的自动归属规则
3. 复测阶段新 Bug 的自动归属规则
