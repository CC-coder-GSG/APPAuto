# 2026-11-3 使用问题修改方案

依据：`2026-11-3问题.md`、五张截图及当前前后端实现。下方保留原实施计划，实际修改与验证记录见第四节。

## 一、现状与处理原则

此前优化解决了需求主列表加载与勾选后的整体重绘。此次第 1 项属于列表显示之后的禅道信息补充请求，需单独优化。第 3 项截图中的 HTTP 500 是接口异常，UI 整理不能代替故障排查。

后续所有刷新都必须保留现有的版本切换保护、卡片展开状态和滚动位置；失败只影响对应区域。读请求可有限重试，写入禅道的操作不盲目自动重试，避免重复工时或重复执行操作。

## 二、分阶段实施

### 第一阶段：加载故障、反馈位置与界面整理（问题 3、4、5、6）

1. 根据请求日志和服务端异常定位截图中 `/workbench/mine` 的 HTTP 500，复现具体版本、最终测试模式和账号场景。当前仅有截图，尚不能断定异常根因；若本地无法复现，需要对应部署版本及异常日志。
2. 建立工作台共享状态显示组件，挂到固定的“我的工作台”标题/导航区域。覆盖需求、复测、测试、任务、审查工作台；显示“需求更新中”“2 项正在处理”等简短信息，点击查看明细。
3. 使用独立任务标识管理状态，多个请求并行时不能被某个请求提前结束提示。区分首次加载、静默更新、写操作、局部失败；切换子页面后仍能查看正在进行的操作。
4. 移除列表上方占整行的“正在更新工作台”提示。首次无数据仍保留原位骨架或加载占位，已有数据更新时保留内容。
5. 反馈待办、指派 Bug 的失败提示改为紧凑、统一的局部提示卡：图标、区域名称、简短原因、文字重试按钮。主列表失败用单独的空状态组件；有旧数据时保留数据并提示更新失败。
6. 各区域的重试只重试对应请求，避免点击“反馈重试”又重载整个工作台。技术错误详情可展开，默认不堆放多行错误文本。
7. 删除需求工作台 Bug 标签最右侧无用途的编辑/删除入口；删除每个需求下重复出现的自动归集说明。保留仍有用途的预览、版本、状态和操作入口。

涉及：`frontend/js/tabs/mine.js`、工作台各 tab、`frontend/index.html`、相关 CSS，新增共享状态/错误展示组件；服务端异常按定位结果修改。

验收：任何子工作台刷新时顶部可见状态；多个刷新互不覆盖；单区域失败不影响其他内容；重试不跳位置；图中两处冗余内容消失。HTTP 500 如已复现，必须增加针对实际根因的回归测试。

### 第二阶段：需求状态和指派人渐进加载（问题 1）

已确认：`zentao-hydrator.js` 把全部未缓存 ID 集中请求，并通过 `Promise.all` 等 Bug 和需求两路返回后才填充；后端批内也等待所有查询完成。即使部分信息已可用，仍可能等待最慢的一项。

修改方案：

- 立即显示已有前端缓存；如本地需求镜像有可信的状态/指派人字段，将其随工作台列表返回作为首屏数据，并标记更新时间。字段缺失时再补充，不根据任务指派人推断需求指派人。
- 需求与 Bug 分别请求、分别渲染，互不等待。
- 按视口优先调度，小批次加载，批次完成立即更新对应标签。初始建议每批 20～30 个、并发 2～3 批，根据实测调整；必须与后端批量上限匹配。
- 共享进行中的同 ID 请求，局部卡片刷新复用请求，避免每张卡片独立发起重复查询。
- 缓存按用户和禅道实例隔离；切换账号、实例及绑定变化时失效。显示缓存的同时后台刷新，不能把失败当作“需求不存在”缓存。
- 明确处理超时、取消、无权限、确实不存在、部分查询失败；只对临时读失败做有限退避重试，鉴权失败引导更新绑定，保留已有可用信息。
- 检查后端 ID 截断处理：超过批量上限不能静默遗漏，再被前端误判为不存在。补齐批次、超时和缺失项的响应约定。

涉及：`frontend/js/zentao-hydrator.js`、`app/api/routes/zentao_hydrate.py`、必要的工作台列表字段及镜像读取。

验收：以 10/50/200 条需求测试；缓存命中立即可见；首批显示不等待最后一批；人为延迟某个 Bug 或需求查询，不阻塞已完成批次；失败仅标记受影响项；版本快速切换无旧结果覆盖；批量超过上限不漏项。记录首个可见标签和可见区域全部标签完成时间，不预先承诺依赖禅道网络的固定秒数。

### 第三阶段：统一图片放大预览（问题 2）

- 在实体预览组件中统一接入图片查看器，覆盖需求、Bug、用例、任务正文及图片附件。
- 点击图片在当前页面上层放大，支持适应窗口、缩放、拖动、上一张/下一张及关闭；移动端至少支持触控缩放与拖动。
- 复用现有带鉴权的图片代理和 Blob 地址，避免点击放大后因直接访问代理地址丢失登录凭据。
- 查看器层级高于实体预览；Esc 先关闭图片查看器，再处理底层预览。关闭图片后保留正文滚动位置。
- 正确处理图片加载失败、切换预览和 Blob 地址释放，避免旧图片覆盖新内容或释放仍在查看的地址。

涉及：`frontend/js/components/entity-preview-modal.js`，新增图片查看组件及样式，复用现有图片请求流程。

验收：正文图片、附件、长图、多图均可放大；关闭后回到原位置；受鉴权保护的图片可用；切换实体和重复开关不串图。

### 第四阶段：耗时禅道操作统一管理（问题 7）

采用“可收起弹窗，操作继续执行”的交互，符合文档希望关闭弹窗后仍可追踪的要求。

操作流程：

1. 提交后按钮显示“正在同步禅道…”并防重复提交；弹窗内部显示清晰状态，顶部工作台区域同步显示该操作。
2. 执行中关闭、点击遮罩或按 Esc 统一作为“收起”。收起不取消请求，也不清空本次表单和目标对象。
3. 点击顶部操作条可重新打开并查看进度。任务保存不可变的实体 ID、操作类型、提交参数和表单快照，避免旧任务回调写入后来打开的另一条记录。
4. 成功：给出带对象名称的成功气泡，仅刷新受影响卡片/工时行；结束对应操作状态。
5. 失败且弹窗仍开着：保留输入并在弹窗内显示错误原因。失败时弹窗已收起：自动恢复该操作弹窗；如用户正在编辑另一个弹窗，显示持久失败提示和“查看并重试”，避免抢占当前编辑。
6. 请求超时或断线时，结果可能尚未确认。先回查禅道实际状态；未确认前不得直接自动重发工时修改、删除等写操作。提供“核对结果”与明确的人工重试入口。

先接入工时编辑/删除、任务开始/暂停/完成/关闭、Bug 关闭/重新激活，再推广到其他同类弹窗。工时组件现有关闭逻辑会清空 editingId/deletingId，需将执行状态与弹窗可见状态拆开。

第一版保证收起弹窗、切换子工作台后继续跟踪；整页刷新或关闭浏览器后的可靠恢复需要服务端持久任务及幂等机制，不应仅靠前端声称支持。若将其纳入需求，应作为本阶段的后续独立改造。

涉及：共享操作状态组件、`modal.js`、`effort-modal.js`、需求/任务工作台、任务看板及 Bug 操作入口；必要的结果回查接口。

验收：慢请求期间提示始终可见；关闭后继续执行；重复点击只产生一次写请求；成功局部更新；失败恢复输入和原因；同时操作不同对象不串结果；超时未确认时不会重复写入。

## 三、交付与回归

建议按上述四阶段分别提交，第一阶段共享状态组件供后续阶段复用。第二阶段性能问题与第四阶段写操作正确性优先投入验证；第三阶段图片功能相对独立，可提前完成。

统一回归门槛：版本切换乱序保护、勾选后的滚动/展开状态、多任务与最终测试、账号绑定失效恢复、多个弹窗操作并行、窄屏布局。采用延迟/失败模拟的真实浏览器测试和必要后端测试；线上性能结论以部署后实际数据为准。

本方案不需要先引入 Redis、额外消息队列或全局页面重构。涉及真实 HTTP 500 的原因、镜像字段是否足够、后端并发预算，在对应阶段开工时进一步核实并记录。

## 四、2026-11-03 实施记录

### 已落地的修改

1. **加载提示与布局**：工作台标题内增加共享活动提示，需求、复测、审查、任务、测试工作台读取及后台禅道同步分别计数。删除需求列表顶部更新动画、Bug 标签编辑/删除符号和重复归集说明。主列表、反馈待办、指派 Bug 使用统一错误卡；辅助区域独立重试，已有卡片不重建。
2. **渐进加载**：需求与 Bug 分别调度，每批最多 20 个 ID、全局最多并行 2 批，视口内优先。批次返回即显示；缓存命中直接显示，过期缓存保留至新数据返回；同一 ID 的进行中请求复用。读取超时 30 秒、临时失败最多重试一次，鉴权失败不自动重试、不缓存为不存在。账号和绑定变化清理缓存及在途结果；后端超过 500 个 ID 明确返回 422，避免静默遗漏。未将任务的指派人误用作需求的指派人。
3. **图片放大**：统一实体预览支持点击图片放大、缩放、拖动、前后切图、键盘和双指操作。复用带鉴权请求取得的 Blob；关闭实体预览释放 Blob URL。Esc 优先关闭图片层，保留需求/Bug 详情。
4. **耗时操作**：新增操作管理器，保存目标对象、提交参数、表单与选择项快照。弹窗收起后继续执行，标题及悬浮入口保留状态；失败保留原输入，若正在编辑另一个对象则不抢占弹窗。共享弹窗的按钮禁用状态按操作归属恢复，旧操作不能覆盖新对象。
5. **接入范围**：工时记录编辑/删除，任务工作台和看板的单任务操作、工时设置与指派，需求任务开始/暂停和测试完成弹窗，需求/测试工作台 Bug 结果保存，以及 Bug 重新激活/指派。需求卡片继续使用已有的局部更新机制保留滚动和展开状态；任务看板及测试总盘刷新对应列表，不执行整页刷新。批量任务操作及创建 Bug 等其他表单沿用现有流程，后续可复用管理器。
6. **不确定写入保护**：断线或 5xx 后只读回查，不自动重发写请求。任务核对实际状态/工时/指派账号，工时核对记录内容与任务状态，Bug 结果同时核对禅道状态及本地小版本、结果、处理结论。总盘新增 `my_minor_version_id` 供精确核对。未确认时保持待核对状态，阻止同一操作再次写入；明确拒绝的请求才开放重试。

### 验证结果

- 后端定向回归：鉴权恢复、Bug 版本、工作台查询、工时、任务和测试总盘，157 项通过。
- 浏览器新增回归 `tests/workbench_async_ui.spec.cjs`：10/50/200/501 个 ID、批量/并发限制、首批渐进显示、缓存与请求复用、鉴权/临时失败、弹窗收起、重复提交、跨对象输入保护、不确定结果回查、图片鉴权复用与 URL 释放、真实 Bug 激活回调、复合写入结果核对。
- 原有浏览器回归通过：工作台加载 9 场景、勾选后位置/展开状态、多任务和最终测试、Bug 版本、需求变更、Token 恢复。
- 本地数据库以只读方式复制到内存检查需求工作台：账号 6 在 16 个已有大版本下读取成功，未写入源数据库。此检查仅覆盖本地列表查询，不代表线上禅道响应耗时。

### 尚需现场确认

- 截图中的 HTTP 500 未在本地复现，不能认定已修复。需要当时版本、账号/模式和服务端异常堆栈继续定位；错误展示优化不替代异常修复。
- 本版操作状态保存在当前页面内，支持收起和切换子工作台，不支持刷新网页、关闭浏览器后的可靠恢复；这需要后端持久操作记录与幂等机制。
- 外部禅道的真实延迟和鉴权故障需部署后观察；模拟测试证明了调度、隔离及保护机制，不承诺固定线上加载秒数。
