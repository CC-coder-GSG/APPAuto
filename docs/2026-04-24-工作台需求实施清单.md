# 工作台需求实施清单

> 日期：2026-04-24
> 目标：把“工作台需求调研”落成可执行的实施任务清单
> 方案口径：仅采用 **禅道 v1 API 拉取式同步**，不再将浏览器推送作为正式路径

## 1. 实施原则

这次实施必须统一遵守以下原则：

1. 禅道接口全部按 `api.php/v1` 设计和验证。
2. 同步方案全部走服务端拉取，不依赖浏览器插件或页面脚本。
3. `Bug` 与 `testcase` 分层建模，不再把工作台关系表当镜像表使用。
4. 工作台的“用例完成”“测试完成”“复测完成”都是业务确认动作，不再承担手工补编号职责。
5. 所有同步都必须可追溯，至少记录：
   - `remote_updated_at`
   - `last_zentao_synced_at`
   - `sync_source`

## 2. 先决策事项

这几项必须先拍板，否则后续开发会反复返工。

### 2.1 requirement 与 testcase 的自动归属规则

必须明确优先级：

1. `story_id == requirement.zentao_story_id`
2. execution / product / plan 辅助归属
3. 管理员人工修正映射兜底

需要确认：

- 是否允许一个 testcase 同时出现在多个 requirement 视图中
- 当禅道 story 变更后，本地 requirement 关系是否自动重算

### 2.2 Bug 的自动归属规则

建议优先级：

1. testcase 关联
2. story 关联
3. requirement 明确映射
4. 人工修正兜底

需要确认：

- 一个 Bug 是否允许同时命中多个 requirement 候选
- 冲突时是“待确认”还是按固定优先级落一个

### 2.3 工作台页面准入校准阈值

建议默认值：

- Bug：最近同步超过 `2` 分钟则先校准
- testcase：最近同步超过 `5` 分钟则先校准

需要确认：

- 是否允许不同软件使用不同阈值

## 3. 数据层实施清单

## 3.1 新增 testcase 镜像表

目标：建立独立的禅道 testcase 同步底座。

建议表名：

- `zentao_testcase_mirror`

建议字段：

- `id`
- `zentao_case_id`
- `zentao_case_numeric_id`
- `zentao_product_id`
- `zentao_product_name`
- `zentao_module_id`
- `zentao_module_name`
- `zentao_story_id`
- `zentao_execution_id`
- `title`
- `type`
- `stage`
- `status`
- `pri`
- `precondition`
- `steps_digest`
- `last_runner_account`
- `last_runner_name`
- `last_run_date`
- `last_run_result`
- `bugs_count`
- `deleted`
- `remote_opened_at`
- `remote_updated_at`
- `last_zentao_synced_at`
- `sync_source`
- `raw_payload`

实施项：

1. 设计 ORM model
2. 设计迁移脚本
3. 为 `zentao_case_numeric_id`、`zentao_story_id`、`zentao_product_id`、`remote_updated_at` 建索引

验收标准：

- 能独立存 testcase，不依赖 requirement 是否已存在

## 3.2 明确保留现有 `test_cases` 的职责

目标：避免镜像层和业务关系层继续混用。

约束：

- `test_cases` 只保留“requirement 与 testcase 的工作台关系”
- 不再作为 testcase 全量同步落库主表

实施项：

1. 梳理所有读取 `test_cases` 的接口和页面
2. 标记哪些逻辑后续改读镜像表
3. 标记哪些逻辑继续读 requirement 关系表

验收标准：

- 后续设计文档里不再把 `test_cases` 当 testcase 镜像表描述

## 3.3 给 Bug 镜像补足同步追踪字段

如果现有 `BugTracking` 已有这些字段，则补齐使用规范；如果缺字段，再补字段：

- `remote_updated_at`
- `last_zentao_synced_at`
- `sync_source`

实施项：

1. 统一定义三个字段的写入时机
2. 统一区分：
   - `scheduled_pull`
   - `on_enter_refresh`
   - `nightly_reconcile`

验收标准：

- 任意一条同步过的 Bug 都能看到最近同步来源与时间

## 4. 同步任务实施清单

## 4.1 新增 testcase 产品级列表拉取服务

目标：让服务端能通过 v1 API 周期拉取 testcase。

接口依据：

- `GET /api.php/v1/products/{productID}/testcases`
- `GET /api.php/v1/testcases/{caseID}`

实施项：

1. 在 `zentao_client_service` 增加：
   - testcase 列表分页拉取
   - testcase 详情获取
2. 统一列表响应解析逻辑：
   - 兼容 `testcases`
   - 兼容 `data`
   - 兼容单对象场景
3. 写 testcase summary normalizer
4. 写 testcase detail hydrator

验收标准：

- 指定产品下的 testcase 能完整分页拉回，并能 upsert 到镜像表

## 4.2 建立 testcase 定时同步任务

建议频率：

- 活跃产品：每 `5` 分钟
- 非活跃产品：每 `15` 分钟
- 夜间全量：每天 `1` 次

实施项：

1. 新增 testcase 定时任务入口
2. 支持按软件映射出禅道产品列表
3. 分页拉取 testcase 列表
4. 首次出现的 testcase 按需补拉详情
5. 记录同步统计：
   - `remote_total`
   - `created`
   - `updated`
   - `deleted_marked`
   - `elapsed_seconds`

验收标准：

- 定时任务完成后，可输出本次同步统计

## 4.3 优化现有 Bug 定时同步任务

目标：把当前已有的全量 Bug 拉取能力，提升为工作台正式数据底座。

实施项：

1. 梳理当前 `overall_test_service` 中的 Bug 拉取链路
2. 抽出“工作台通用同步服务”，避免整体测试独占
3. 区分：
   - 白天常态拉取
   - 夜间全量对账
4. 对关闭、激活、指派、删除状态做一致性更新

验收标准：

- 不依赖页面操作，也能持续把 Bug 状态拉齐到本地

## 4.4 新增工作台进入前轻量校准

目标：不依赖浏览器推送，也尽量减少用户感知延迟。

建议逻辑：

1. 用户进入需求工作台/复测工作台/用例中心
2. 服务端检查当前软件最近同步时间
3. 若超过阈值，则只拉当前软件相关产品
4. 若页面是 requirement 视图，则优先校准与该 requirement 相关的数据

实施项：

1. 定义 freshness 判断函数
2. 定义校准阈值配置
3. 定义轻量校准范围
4. 给页面首屏请求增加“必要时先校准”能力

验收标准：

- 用户进入工作台时，如果本地数据过旧，会先刷新再返回页面数据

## 5. 归属关系实施清单

## 5.1 requirement 与 testcase 自动建联

目标：让工作台不再依赖人工录 testcase 编号。

实施项：

1. 根据 `story_id` 建主归属规则
2. 补 execution / product / plan 辅助规则
3. 输出 requirement 与 testcase 的候选关系
4. 生成 requirement 工作台所需的“最终可展示 testcase 集合”

验收标准：

- requirement 卡片能自动展示 testcase 集合，不需要手工新增

## 5.2 requirement 与 Bug 自动建联

目标：让工作台不再依赖人工录 Bug 编号。

实施项：

1. 先根据 testcase 关系反推 Bug
2. 再根据 story 归属补充 Bug
3. 对冲突归属生成待确认项
4. 输出 requirement 维度的最终 Bug 集合

验收标准：

- requirement 卡片能自动展示关联 Bug 集合，不需要手工新增

## 5.3 复测证据集合自动生成

目标：复测工作台改成“自动归集证据 + 人工裁决”。

实施项：

1. 汇总 requirement 下原测试阶段 Bug
2. 汇总 testcase 关联 Bug
3. 汇总测试完成后新出现且归属于该 requirement 的 Bug
4. 输出复测证据集合

验收标准：

- 复测页面默认就能列出打回/通过判断所需证据

## 6. 页面与接口实施清单

## 6.1 新增“用例中心”页面

目标：提供独立 testcase 浏览入口。

页面能力：

1. 按软件/产品/模块/需求/状态筛选
2. 展示编号、标题、所属需求、优先级、阶段、最近执行结果、最近执行时间
3. 支持查看 testcase 详情
4. 支持跳转 requirement / 复测 / 整体测试

接口能力：

1. 用例列表
2. 用例详情
3. 最近同步时间
4. requirement 归属信息

验收标准：

- 测试人员不进入禅道，也能在系统内浏览 testcase

## 6.2 改造需求工作台

目标：去掉手工录编号主流程。

要移除或弱化的入口：

- 逐个添加用例
- 手工添加自由 Bug
- 手工给用例录入 Bug 编号

保留的业务动作：

- 用例完成
- 测试完成
- 测试要点维护

改造后流程：

1. requirement 卡片自动展示 testcase 集合
2. requirement 卡片自动展示 Bug 集合
3. 用户只做确认与填写测试结论

验收标准：

- 普通测试用户完成需求测试，不需要再手工补编号

## 6.3 改造复测工作台

目标：把复测页面从“手工记录证据”改成“证据自动归集”。

要移除或弱化的入口：

- 手工新增“复测新增 Bug”作为主流程

保留的业务动作：

- 标记旧 Bug 未修好
- 确认新 Bug 是否归属当前 requirement
- 提交通过/打回

验收标准：

- 复测人员进入页面后，默认已看到待判定证据集合

## 6.4 保留管理员兜底修正入口

目标：主流程自动化，但保留异常修正能力。

建议位置：

- 同步中心
- 或单独的“映射修正”管理面板

允许操作：

- 修正 testcase 归属
- 修正 Bug 归属
- 处理冲突候选

验收标准：

- 自动规则覆盖不了的场景，管理员仍可人工修正

## 7. 测试与验收清单

## 7.1 接口级验收

需要覆盖：

1. v1 token 获取成功/失败
2. Bug 列表分页拉取
3. testcase 列表分页拉取
4. testcase 详情补拉
5. token 失效后自动刷新
6. 删除/关闭状态同步

## 7.2 数据级验收

需要覆盖：

1. 同一条 Bug / testcase 重复同步不生成重复记录
2. 状态变更能正确覆盖
3. requirement 自动归属正确
4. 冲突场景能进入待确认而不是直接丢失

## 7.3 页面级验收

需要覆盖：

1. 用例中心能正常筛选和查看详情
2. 需求工作台进入时能触发轻量校准
3. requirement 卡片不再要求手工录用例/Bug
4. 复测工作台能自动生成证据集合

## 7.4 业务级验收

需要抽真实需求做回归：

1. 新建 testcase 后，工作台能在可接受时间内看到
2. 新建 Bug 后，工作台能在可接受时间内看到
3. Bug 关闭后，相关工作台和报表口径一致
4. requirement 测试完成后，复测工作台能拿到对应证据

## 8. 推荐实施顺序

不要并行铺太开，建议按下面顺序推进：

### 第一阶段：数据底座

1. 拍板归属规则
2. 新增 testcase 镜像表
3. 补 testcase v1 拉取能力
4. 规范 Bug 同步追踪字段

### 第二阶段：同步链路

1. 上 testcase 定时同步
2. 整理 Bug 定时同步
3. 新增工作台进入前轻量校准
4. 补夜间全量对账

### 第三阶段：关系归属

1. requirement 与 testcase 自动建联
2. requirement 与 Bug 自动建联
3. 复测证据集合自动生成

### 第四阶段：页面改造

1. 新增用例中心
2. 改造需求工作台
3. 改造复测工作台
4. 保留管理员修正入口

### 第五阶段：联调验收

1. 跑真实软件数据回归
2. 校验同步时效
3. 校验工作台业务流程
4. 校验报表口径是否受影响

## 9. 风险提醒

这几个风险建议提前盯住：

1. 禅道 v1 testcase 列表字段形态可能比 Bug 更不稳定，解析层要做兼容。
2. requirement 自动归属规则如果没先定清，后面页面改造都会反复返工。
3. 如果不给“冲突归属”设计待确认状态，自动规则一旦误判，业务会直接不信任系统。
4. 如果页面准入校准范围太大，会拖慢首屏；太小，又起不到 freshness 作用。

## 10. 建议的第一批开发任务

如果现在要正式开工，我建议第一批直接拆成下面 8 个任务：

1. 定稿 testcase / Bug 自动归属规则。
2. 新增 `zentao_testcase_mirror` 表和索引。
3. 在 `zentao_client_service` 增加 v1 testcase 列表与详情拉取。
4. 新增 testcase 定时同步服务。
5. 抽离工作台通用的 Bug 同步服务，脱离整体测试专用语义。
6. 新增 freshness 判断与“进入工作台前轻量校准”。
7. 实现 requirement 与 testcase / Bug 的自动建联查询。
8. 新增“用例中心”列表与详情接口。
