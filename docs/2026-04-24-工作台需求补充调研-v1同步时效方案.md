# 工作台需求补充调研：v1 API 与同步时效方案

> 调研日期：2026-04-24
> 补充问题：
> 1. Bug 和用例如何有效同步，确保测试人员进入工作台时能及时、准确看到已提交信息
> 2. 当前禅道实际使用的是 v1 API，之前引用到的 v2 资料需要纠偏

## 1. 先说结论

这两个问题的结论都比较明确：

1. 你们当前系统和当前禅道接口口径，应该以 **RESTful API v1** 为准，不应该再按 v2 设计主方案。
2. 如果浏览器推送这条路明确排除，那么最稳的正式方案应当是纯 **拉取式同步**：
   - **服务端 v1 API 定时拉取** 负责常态同步
   - **进入工作台前的轻量校准** 负责当前页面可见范围的 freshness
   - **夜间全量对账** 负责最终一致性和兜底

也就是说，推荐走 **Scheduled Pull + On-Enter Refresh + Nightly Reconcile** 的同步架构。

## 2. 关于 API 版本：当前应以 v1 为准

你这个判断是对的。当前系统本地代码本身就明确写死在 v1 上：

- `app/services/zentao_auth_service.py`
  - 取 token 用的是 `POST /api.php/v1/tokens`
- `app/services/zentao_client_service.py`
  - `_api_base = {base_url}/api.php/v1`
- `app/services/overall_test_service.py`
  - 当前全量 Bug 拉取走的是 `products/{id}/bugs`
- `app/services/requirement_service.py`
  - 同步需求时也通过 v1 client 调执行、需求相关接口

所以后续设计 testcase / bug 同步时，应该统一按 v1 做能力边界确认。

## 3. 禅道官方 v1 能力确认

### 3.1 v1 Token

禅道官方 v1 文档：

- `POST /api.php/v1/tokens`
- 请求体：`account`、`password`
- 返回：`token`

来源：
- https://www.zentao.net/book/apidoc-v1/664.html
- https://www.zentao.net/book/api/1397.html

### 3.2 v1 Bug 列表

禅道官方 v1 文档：

- `GET /api.php/v1/products/id/bugs`
- 响应包含：
  - `page`
  - `total`
  - `limit`
  - `bugs`

来源：
- https://www.zentao.net/book/apidoc-v1/720.html
- https://www.zentao.net/book/api/1397.html

这和当前系统已有实现是一致的。  
`overall_test_service.py` 里已经在用这个接口做全量 Bug 拉取。

### 3.3 v1 用例列表

禅道官方 v1 文档：

- `GET /api.php/v1/products/id/testcases`
- 响应包含：
  - `page`
  - `total`
  - `limit`
  - `testcases`

来源：
- https://www.zentao.net/book/api/725.html?fullScreen=y0YFe6NV

这说明 testcase 的产品级分页同步在 v1 下也是可行的。

### 3.4 v1 用例详情

禅道官方 v1 文档：

- `GET /api.php/v1/testcases/id`

返回字段里包含：

- `story`
- `title`
- `precondition`
- `steps`
- `openedBy`
- `openedDate`
- `status`
- `lastRunner`
- `lastRunDate`
- `lastRunResult`

来源：
- https://www.zentao.net/book/api/727.html?fullScreen=zentao&theme=default

这意味着 testcase 的“列表同步 + 详情补拉”在 v1 里是可以成立的。

## 4. 现有系统已经有的同步基础

### 4.1 当前已有浏览器同步中心，但不建议再作为正式方案

当前系统已经存在浏览器同步中心：

- `app/api/routes/zentao_sync.py`
  - 支持 `bug`
  - 支持 `testcase`
- `app/services/zentao_sync_service.py`
  - 可以接收浏览器事件
  - 可以映射 requirement
  - 可以落本地

这条链路说明系统过去尝试过事件驱动同步，但如果从产品化和稳定性角度看，它更适合作为历史能力说明，而不是后续正式架构。

### 4.2 Bug 拉取链路已经具备正式方案基础

当前系统已经有服务端主动拉 Bug 的实现：

- `app/services/overall_test_service.py`
  - `sync_all_zentao_bugs_by_software()`
  - 已经按产品维度拉 `/products/{id}/bugs`
  - 已经做了分页、去重、upsert、token 失效重试、状态归一

这说明：

- Bug 侧服务端拉取不是从零开始
- 真正缺的是 testcase 的同等级拉取链路，以及更适合工作台的时效策略

### 4.3 当前缺的是 testcase 拉取同步与工作台校准机制

现在 testcase 侧缺少：

- 定时拉取同步
- 进入工作台时的轻量校准
- 独立 testcase 镜像层

## 5. 为什么推荐纯拉取式同步

### 5.1 浏览器推送不适合作为正式架构

如果浏览器推送被排除，原因本身也是成立的：

1. 依赖浏览器脚本、插件、前端页面环境，链路更脆弱
2. 运维和排错复杂，问题容易落在“到底是禅道没变、插件没发、还是服务端没收”
3. 多账号、多浏览器、多入口场景下不可控
4. 对工作台这种核心业务数据链路来说，不够优雅，也不够稳定

所以正式方案更适合收敛到服务端可控的 API 拉取。

### 5.2 纯定时拉取会有时延，但这个问题可以通过页面准入校准解决

只靠后台 cron 式同步会有一个天然问题：

1. 用户刚在禅道提完 Bug
2. 下一次定时任务还没跑
3. 工作台短时间内看不到

这个问题不需要靠浏览器推送解决，也可以通过“进入工作台前轻量校准”解决。

### 5.3 最合理的是“周期拉取 + 页面校准 + 夜间对账”

因此推荐：

1. **周期拉取** 负责常态同步
2. **进入工作台前轻量校准** 负责缩短用户感知延迟
3. **夜间全量对账** 负责最终一致性

## 6. 推荐同步架构

## 6.1 总体架构

建议把同步拆成三层：

### 第一层：周期拉取层

来源：

- v1 REST API

目标：

- 周期性把产品下的 Bug/testcase 拉全
- 修复浏览器事件漏掉的数据
- 同步关闭、删除、改标题、改归属等变更

特点：

- 2 到 5 分钟级
- 负责主同步

### 第二层：工作台进入前轻量校准层

来源：

- 前端进入工作台时触发后端轻量同步

目标：

- 如果最近一次同步距离现在太久，就先快速校准再展示

特点：

- 只同步当前软件/当前产品/当前 requirement 相关数据
- 避免“明明刚提交，工作台还没刷新”

### 第三层：夜间全量对账层

来源：

- v1 REST API 全量分页拉取

目标：

- 修正漏同步、状态漂移、删除漏记、归属变更等问题

特点：

- 每天 1 次
- 负责最终一致性兜底

## 6.2 Bug 数据同步建议

### 常态同步路径

服务端按产品周期性拉取：

- `GET /api.php/v1/products/{productID}/bugs`

推荐频率：

- 活跃产品：`2` 分钟一次
- 非活跃产品：`10` 到 `15` 分钟一次
- 夜间全量校准：每天 `1` 次

推荐同步规则：

1. 按 `zentao_bug_id` 做幂等 upsert
2. 更新以下字段：
   - 标题
   - 状态
   - 指派人
   - 关闭人/关闭时间
   - story/execution/build/product 归属
   - 删除标记
3. 记录：
   - `remote_updated_at`
   - `last_zentao_synced_at`
   - `sync_source`（browser_event / periodic_pull / on_enter_refresh）

### 进入工作台前校准

当前用户打开需求工作台、复测工作台前：

如果命中以下条件之一，就先对相关产品做一次轻量拉取：

1. 该软件最近一次 Bug 同步已超过 `2` 分钟
2. 当前 requirement 最近一次相关 Bug 校准已超过阈值
3. 当前工作台查询范围存在“同步时间早于页面阈值”的数据

这样可以在不依赖浏览器推送的前提下，把用户感知延迟压到可接受范围。

## 6.3 testcase 数据同步建议

### 常态同步路径

服务端新增 testcase 周期拉取任务：

- `GET /api.php/v1/products/{productID}/testcases`

推荐频率：

- 活跃产品：`5` 分钟一次
- 非活跃产品：`15` 分钟一次
- 夜间全量校准：每天 `1` 次

推荐原因：

1. testcase 变动频率通常比 Bug 低
2. 用例详情字段更重，没必要像 Bug 一样高频拉全量详情

### 列表与详情分离

建议 testcase 采用两段式同步：

1. **列表同步**
   - 拉产品 testcase 列表
   - 写入 testcase 镜像表的轻量字段
2. **详情补拉**
   - 新 testcase 首次出现时补一次详情
   - 用户点开用例详情时补一次详情
   - 如果后续识别到它发生变化，再补详情

这样做的好处：

- 列表页快
- 同步成本低
- 又不影响详情完整度

## 7. 怎样保证“及时且准确”

如果目标是让测试人员进入工作台时能及时、准确确认数据，我建议把标准定义成三层：

### 7.1 分钟级常态标准

Bug：

- 活跃产品在 `2` 分钟级别内同步到本地

testcase：

- 活跃产品在 `5` 分钟级别内同步到本地

### 7.2 页面准入校准标准

如果当前 requirement / 当前软件最近同步过旧：

- 先跑一次轻量校准，再渲染工作台

### 7.3 夜间最终一致性标准

每天至少一次：

- 全产品全量 Bug 对账
- 全产品全量 testcase 对账

这样可以做到：

- 白天常态数据延迟可控
- 用户真正进入工作台前还能再校准一次
- 漏掉的数据不会长期缺失

## 8. 关键设计点

## 8.1 必须做幂等 upsert

Bug 和 testcase 同步都必须按禅道主键做幂等：

- Bug：`zentao_bug_id`
- testcase：`zentao_case_numeric_id` 或标准化后的 `zentao_case_id`

不能按“谁触发同步”“谁当前登录”去生成记录。

## 8.2 必须保留远端更新时间与本地同步时间

至少要保存：

- `remote_updated_at`
- `last_zentao_synced_at`
- `sync_source`

这样后续才能判断：

- 哪条数据是旧的
- 哪条数据只是还没来得及同步
- 哪条数据来自定时拉取，哪条数据来自页面校准

## 8.3 必须保留未映射数据，不要丢

有些 Bug/testcase 第一次进来时，系统未必马上能归到某个 requirement。  
这种情况下应该：

- 先进入镜像表
- 再进入待映射队列

而不是因为“暂时不知道归属”就不落库。

## 8.4 必须保留夜间全量校准

即使有实时事件和分钟级定时拉取，也建议每天至少一次：

- 全产品全量 Bug 校准
- 全产品全量 testcase 校准

原因很简单：

- 删除、历史改动、权限变化、脚本漏报，这些都需要有最后兜底

## 9. 基于当前系统的落地建议

## 9.1 Bug 侧

当前已经有全量 Bug 拉取实现，建议直接复用并升级成拉取式三层架构：

1. 保留并扩展 `/products/{id}/bugs` 的定时拉取
2. 给工作台加“进入前轻量校准”
3. 增加夜间全量对账

这部分不是重做，是强化现有能力。

## 9.2 testcase 侧

testcase 侧目前还缺：

1. 服务端产品级列表拉取
2. testcase 镜像表
3. 详情按需补拉
4. 工作台进入前校准

所以 testcase 侧是这次新增工作的重点。

## 9.3 工作台侧

工作台不要再直接依赖“用户手工录编号”，而应该依赖：

1. 已同步的 Bug 镜像
2. 已同步的 testcase 镜像
3. requirement 与 story/testcase 的映射关系

并在进入页面前做一次 freshness check。

## 10. 最终建议

针对你这次提出的两个疑问，我的最终建议是：

1. **版本口径统一改成 v1**
   - 后续方案、文档、接口设计都按 `api.php/v1` 走
   - 先不要再拿 v2 作为实现依据

2. **同步策略采用纯拉取式三层模式**
   - v1 API 定时拉取：解决“常态同步”
   - 进入工作台前校准：解决“最后一跳延迟”
   - 夜间全量对账：解决“完整性与纠偏”

3. **Bug 和 testcase 不要用同一个频率**
   - Bug 更活跃，建议 `2` 分钟级
   - testcase 相对低频，建议 `5` 分钟级

4. **testcase 仍然要做镜像层**
   - 否则无法把“及时”和“准确”同时做好
