## 一、结论先说

本次问题修复建议拆成两部分：

1. **代码层止血**
   把系统内所有错误使用 `datetime.utcnow()` 的“本地业务时间”改为统一的本地时间函数，避免继续写入慢 8 小时的新数据。

2. **数据层修复历史脏数据**
   不能直接“全库所有 DATETIME 字段统一 +8 小时”，必须按字段来源分三类处理：
   - **A类：本系统本地写入时间**  
     这类字段可以直接批量 `+8 hours`。
   - **B类：禅道同步来的外部时间**  
     这类字段不建议直接平移，应该以禅道为准重新同步覆盖。
   - **C类：业务手工录入/内部鉴权时间**  
     这类字段不能机械平移，需要保留或单独处理。

如果按这个方案执行，能同时解决：

- 以后新增/修改的数据不再继续错 8 小时
- 现在库里已经写错的本地时间被补正
- 不会把禅道原始时间和业务录入时间一起修坏

### 2. 不要直接加 8 小时，应该重新从禅道同步的字段

这些字段不是系统自己生成的，而是**禅道返回的业务时间**。如果直接统一平移，风险是把本来正确的数据修错。

本库这类非空值共 **110** 个：

| 表 | 字段 | 处理方式 |
|---|---|---|
| `bug_tracking` | `zentao_close_date` | 以禅道重新同步覆盖 |
| `bug_tracking` | `zentao_remote_updated_at` | 以禅道重新同步覆盖 |

建议做法：

- 先上线代码修复
- 再执行一次 Stage5 禅道全量同步
- 用禅道最新返回值覆盖本地缓存字段

### 3. 不能机械平移的字段

这些字段不是“系统错误写入的当前时间”，而是**业务输入时间或鉴权内部时间**：

| 表 | 字段 | 原因 |
|---|---|---|
| `field_test_records` | `start_time`, `end_time` | 这是用户录入的测试起止时间，不是 `utcnow()` 自动生成 |
| `user_zentao_bindings` | `token_expires_at` | 这是 token 过期时间，属于鉴权内部逻辑，不建议通过 SQL 平移修复 |

其中 `token_expires_at` 的处理建议是：

- 上线时直接清空 `token_value/token_expires_at`
- 让系统重新换 token
- 避免新旧逻辑混用导致“误判已过期/未过期”

## 四、推荐落地方案

### Phase 1：先修代码，停止继续写错

不要继续直接使用 `datetime.utcnow()` / `datetime.now()` 到处散写，建议统一收口成一个时间工具，例如：

```python
# app/utils/time_utils.py
from datetime import datetime

def local_now() -> datetime:
    return datetime.now()
```

然后把以下两类全部替换：

- 模型默认值：`default=datetime.utcnow` / `onupdate=datetime.utcnow`
- 服务层赋值：`datetime.utcnow()`

#### 代码修复范围

1. **业务时间统一改成本地时间**
   适用于 `created_at`、`updated_at`、`handled_at`、`retested_at`、`executed_at`、`last_zentao_synced_at` 这类字段。

2. **缓存/TTL 比较逻辑也要一起改**
   例如 `app/services/stage5_service.py` 中 `_sync_cache` 的比较逻辑，写入和比较必须使用同一套时间基准。

3. **`zentao_auth_service.py` 单独处理**
   这个文件不能简单照抄“全部改 `datetime.now()`”：
   - token 过期时间最好统一用一套明确逻辑
   - 如果仍然使用 naive datetime，就必须在“写入”和“比较”两边同时改成本地时间
   - 更稳妥的是：**鉴权内部继续按 UTC 处理，但不要把这个时间拿去前台展示**

我的建议是：

- **业务数据时间**：统一本地时间
- **鉴权/token 内部时间**：保留 UTC 语义或上线后直接清缓存重拿

### Phase 2：备份数据库

执行任何历史时间修复前，先完整备份：

```powershell
Copy-Item .\app_auto.db .\app_auto_2026-04-17_before_time_fix.db
```

如果在线上环境操作，再额外做一份压缩备份。

### Phase 3：执行历史数据修复脚本

建议不要手工一条条写 SQL，直接做一个一次性迁移脚本，例如：

- `scripts/fix_local_time_offset.py`

脚本职责：

1. 开事务
2. 逐表逐字段执行 `+8 hours`
3. 记录每张表、每个字段的影响行数
4. 成功后提交，失败则回滚

SQL 形式大致如下：

```sql
UPDATE audit_logs
SET created_at = datetime(created_at, '+8 hours')
WHERE created_at IS NOT NULL;
```

需要注意：

- SQLite 的 `datetime()` 会丢失微秒精度
- 如果你希望尽量保留原格式，建议用 Python 脚本读出后用 `datetime + timedelta(hours=8)` 再回写
- 因为当前库里很多值带微秒，**更推荐 Python 脚本迁移，不推荐纯 SQL**

### Phase 4：清理/刷新禅道相关时间

对 `bug_tracking` 表中的以下字段不要执行 `+8 hours`：

- `zentao_close_date`
- `zentao_remote_updated_at`

处理方式：

1. 部署代码修复
2. 执行一次 Stage5 的禅道全量同步
3. 用同步回来的时间覆盖本地缓存

如果担心旧值残留，可先置空再同步：

```sql
UPDATE bug_tracking
SET zentao_close_date = NULL,
    zentao_remote_updated_at = NULL
WHERE zentao_bug_id IS NOT NULL;
```

然后马上触发全量同步回填。

### Phase 5：清空 token 缓存

建议上线后顺手处理：

```sql
UPDATE user_zentao_bindings
SET token_value = NULL,
    token_expires_at = NULL;
```

原因：

- 避免旧 token 的过期时间仍按旧时基解释
- 重新获取 token 的成本很低
- 这是最稳的切换方式

## 五、为什么不建议“全库所有时间字段统一 +8 小时”

因为至少有三类字段会被误伤：

1. **禅道原始时间**
   例如 `zentao_close_date`，应以禅道返回值为准，不应二次加工。

2. **业务录入时间**
   例如 `field_test_records.start_time/end_time`，这是人工填写的测试开始/结束时间。

3. **鉴权内部时间**
   例如 `token_expires_at`，它是内部判断依据，不是用户看到的业务时间。

所以这次修复必须是**分组修复**，不能粗暴全量平移。
