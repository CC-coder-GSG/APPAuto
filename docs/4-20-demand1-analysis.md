# 4-20需求1问题原因与解决方案

## 文档目的

本文只整理问题原因、改造思路和推荐解决方案，不直接修改业务代码。

对应需求来源：`docs/4-20需求1.md`

---

## 一、将“我的工作台 / 复测工作台 / 整体测试”整合为统一工作台

### 1. 当前代码现状

当前这三个页面仍然是三个并列的一级 Tab，而不是一个统一工作台下的子页面。

现状证据：

- 顶部导航中，三者分别是独立按钮：
  - `frontend/index.html` 中存在 `tabMineBtn`、`tabRetestBtn`、`tabOverallTestBtn`
- 页面结构中，三者分别对应独立 section：
  - `#tab-mine`
  - `#tab-retest`
  - `#tab-overall-test`
- 全局切页逻辑 `showTab(name)` 也是按一级页面独立切换这三个 section

这说明当前系统的页面组织方式是：

- 一级导航直接切换“需求工作台 / 复测工作台 / 测试工作台（原整体测试）”
- 每个模块分别拥有自己的 DOM、加载入口、筛选逻辑和 SSE 未读清理逻辑

这也是为什么它们现在“功能独立、实现稳定”，但不满足“统一工作台 + 子页面”的交互要求。

---

### 2. 需求本质

你要的不是简单改名字，而是结构升级：

- 一级 Tab 只保留一个“我的工作台”
- 在“我的工作台”内部再拆成 3 个子页面：
  - 需求工作台（原我的工作台）
  - 复测工作台（原复测工作台）
  - 测试工作台（原整体测试）
- 子页面切换时有左右滑动动画
- 原三个页面的功能逻辑不变
- UI 风格保持统一

这本质上是“导航层级调整 + 容器重构 + 动画补充”，不是业务规则重写。

---

### 3. 当前实现为什么不能直接满足需求

主要原因有 4 个：

#### 原因 1：三个页面是独立一级路由式切换，不是同一容器内切换

当前 `showTab(name)` 是按一级页面切换 section 的。也就是说：

- `mine`、`retest`、`overall-test` 是同层级页面
- 不存在“工作台父容器 + 子页面”的布局

因此如果只改按钮文字而不改结构，页面关系仍然是平级，不是真正的统一工作台。

#### 原因 2：三个模块的加载入口分散

当前加载方式分别是：

- 我的工作台：`loadMyWorkbench()`
- 复测工作台：`loadRetest()`
- 整体测试：`loadOverallTest()`

这些函数在 `showTab(name)` 中被分别触发。

如果改成统一工作台，需要重新定义：

- 一级 Tab 打开时加载哪个子页
- 子页切换时调用哪个原有加载函数
- 子页切换是否保留原来的筛选条件和滚动位置

#### 原因 3：三个模块有各自的未读/SSE 作用域

当前 SSE 角标和“进入页面后清空未读”的逻辑也是按一级 Tab 分开的：

- `mine_requirement`
- `retest_requirement`
- `overall_bug`

如果直接把三个 section 堆进一个页面但不重构子页切换逻辑，会出现：

- 未读角标清理时机不准确
- 进入工作台父页后，不知道应该清理哪个子页作用域
- 用户停留在工作台父页但不在对应子页时，状态和视觉不一致

#### 原因 4：滑动动画要求的是“子页面容器切换”，不是简单 show/hide

当前 section 切换本质是 `hidden/classList` 显隐。

这种方式：

- 适合一级页面切换
- 不适合做稳定的左右滑动动画

因为滑动动画通常需要：

- 一个固定宽度的父级 viewport
- 一个横向排布的 track
- 每个子页固定宽度占位
- 切换时对 track 做 `transform: translateX(...)`

当前结构没有这个容器层。

---

### 4. 推荐解决方案

推荐采用“低风险重构”，而不是重写三个模块。

#### 方案核心

保留原三个模块的 JS 逻辑和数据加载函数不变，只调整页面组织方式：

- 一级导航中移除独立的 `复测工作台` 和 `整体测试` 按钮
- 一级导航只保留一个 `我的工作台`
- 在 `#tab-mine` 内部新增一个“子工作台切换器”
- 将原 `#tab-retest` 和 `#tab-overall-test` 的内容迁移/挂载到 `#tab-mine` 内部的三个子面板中
- 子页面切换只负责：
  - 切换可见面板
  - 调用原有加载函数
  - 触发对应未读清理
  - 触发 CSS 横向滑动动画

#### 推荐子页面命名

- 需求工作台：承接原 `mine`
- 复测工作台：承接原 `retest`
- 测试工作台：承接原 `overall-test`

#### 页面结构建议

在 `#tab-mine` 下新增：

- 子导航条
- 滑动容器 viewport
- 横向 track
- 3 个子面板 panel

建议结构：

- `workbench-shell`
- `workbench-subnav`
- `workbench-viewport`
- `workbench-track`
- `workbench-panel demand`
- `workbench-panel retest`
- `workbench-panel overall-test`

#### 动画建议

使用 CSS 过渡即可，不建议引入额外动画库：

- `display:flex` 横向布局 track
- 每个 panel `width:100%`、`flex-shrink:0`
- track 切换时做 `transform: translateX(0 / -100% / -200%)`
- 添加 `transition: transform 240ms ease`

这样可以满足你要的“左右滑动过渡”，且实现成本低。

---

### 5. 推荐实施顺序

1. 先把导航结构改成“一级我的工作台 + 内部 3 子页”
2. 再把原 `mine / retest / overall-test` 的 section 内容挂到统一容器里
3. 保留原加载函数和原模块 namespace，不先改业务逻辑
4. 再补子页切换状态管理
5. 最后补滑动动画和 UI 对齐

---

### 6. 风险点

#### 风险 1：直接复制 DOM 容易把事件绑定弄乱

如果是“复制内容”而不是“重构容器”，容易出现：

- 原按钮 `onclick` 还在，但元素 ID 重复
- 同一模块函数引用到旧 DOM ID
- 加载成功但交互不稳定

所以不建议简单复制 HTML，而应当做“原内容迁移到统一容器”或“保留唯一 DOM ID 的子容器重构”。

#### 风险 2：默认子页和未读清理逻辑容易混乱

进入统一工作台时，需要明确：

- 默认展示哪个子页
- 是否记忆用户上次停留的子页
- 清空未读时按“进入父页”还是“进入具体子页”处理

推荐做法：

- 记忆上次子页
- 真正切到某个子页时才清理该子页未读

#### 风险 3：高度差异会导致滑动体验不稳

三个子页高度差异很大，尤其：

- 需求工作台是卡片流
- 复测工作台也是卡片流
- 测试工作台是表格布局

如果 track / viewport 高度没处理好，会出现切换时抖动、裁切或滚动条闪烁。

推荐做法：

- viewport 不固定死高度
- 切页后根据当前子面板内容自动撑高
- 不强行把三个页面锁死成同高容器

## 二、频繁筛选/切换版本后，Bug 的禅道状态、解决状态、激活状态、指派人加载不稳定

### 1. 现象复述

你描述的问题是：

- 频繁筛选 Bug 列表
- 频繁切换版本
- 每次列表刷新后，都会尝试重新从禅道补充状态信息
- 但频繁操作之后，部分 Bug 的这些信息不稳定：
  - 已关闭 / 已解决 / 激活
  - 当前指派给谁
- 表现为有时能加载出来，有时加载不完整

这个问题的核心不在后端筛选，而在前端的禅道 hydration 并发控制。

---

### 2. 当前代码中的直接根因

#### 根因 1：禅道 hydrator 使用了“全局单例 AbortController”

在 `frontend/js/zentao-hydrator.js` 中，当前实现有一个全局变量：

- `_activeAbort`

每次调用 `hydrateContainer(containerEl)` 时，都会：

- 先 `abort` 上一次仍在进行中的 hydration 请求
- 再为当前请求创建新的 AbortController

这意味着：

- 任何一次新的 hydrate 调用
- 都会中断前一次未完成的请求

如果用户频繁操作：

- 筛选一次触发 hydrate
- 切版本再触发 hydrate
- 再筛选又触发 hydrate

那么前面的请求会不断被后面的请求打断。

这会带来两个结果：

- 某些 Bug 槽位还没来得及填充就被取消
- 状态/指派人/解决方案等禅道补充信息显示不完整

#### 根因 2：同一个容器正在加载时，新一次 hydrate 直接被跳过

当前代码还用 `_pendingContainers` 防止重复请求。

逻辑是：

- 如果某个 container 正在 hydrate
- 再次调用 `hydrateContainer(containerEl)` 时，会直接 return

这在“同一容器频繁重绘”的情况下反而会出问题：

- 旧请求还没完成
- 列表 DOM 已经被新筛选结果重绘了
- 新列表本应重新触发 hydration
- 但因为容器被标记为 pending，新 hydrate 被跳过

结果就是：

- 新 DOM 上的 `zt-bug-slot` 没有真正进入最新一次加载流程
- 列表刷新了，但禅道状态没跟上

#### 根因 3：当前设计是“容器级抢占”，不是“容器级版本化”

现在的策略是：

- 不是“只保留最新一次结果”
- 而是“新请求打断旧请求 / 或新请求被跳过”

这是典型的并发控制不完整。

正确思路应当是：

- 每个容器独立维护自己的请求序号或 abort controller
- 新请求只取消“同一个容器”的上一个请求
- 不应该让别的容器或别的页面的 hydration 干扰当前容器

#### 根因 4：Mine / Retest / Overall-Test 三个页面都共用同一个 hydrator

当前这些页面都会在渲染后调用：

- `window.OmniQAZentao?.hydrateContainer(...)`

也就是说：

- 我的工作台刷新一次，会占用 hydrator
- 复测工作台刷新一次，也会占用 hydrator
- 整体测试刷新一次，还是同一套 hydrator

如果统一工作台改造后还不调整 hydrator 并发模型，这个问题只会更明显。

---

### 3. 为什么你看到的是“状态/指派没出来”，而不是“整个列表报错”

因为当前 hydrator 的失败模式不是整页崩溃，而是“部分 slot 填充失败”：

- 表格/卡片本地数据仍然能渲染
- 禅道补充状态是后置填充
- 请求一旦被取消或跳过，只是 slot 没被补全
- 页面整体看起来仍然能用，只是细节信息缺失

所以从现象上看，就是：

- Bug 还在
- 但状态、解决情况、指派人不完整

这和你的现场观察是一致的。

---

### 4. 推荐解决方案

#### 方案 1：把全局 `_activeAbort` 改成“按容器维度管理”

当前最需要改的是这一点。

推荐做法：

- 不再使用一个全局 `_activeAbort`
- 改成 `WeakMap<Element, AbortController>` 或等价结构
- 每个 container 拥有自己的请求控制器

这样做的结果：

- 整体测试自己的刷新，只会取消整体测试上一次未完成请求
- 不会把我的工作台/复测工作台的请求一起打断
- 统一工作台改造后，三个子页也能独立控制 hydration

这是最关键的一步。

#### 方案 2：把 `_pendingContainers` 从“直接跳过”改成“最新请求覆盖旧请求”

不要在容器 pending 时直接 return。

推荐做法：

- 每个容器维护一个 `requestVersion`
- 发起请求时记录当前版本号
- 请求返回时只处理“仍然是最新版本”的结果
- 如果中途又来了新请求，则旧结果自动丢弃

这样能保证：

- 最终一定是最后一次筛选/切换对应的数据落到页面上
- 不会因为 pending 机制把新 DOM 的 hydration 直接跳过

#### 方案 3：对频繁操作做轻量 debounce

对于这些触发点，建议增加轻量防抖：

- 筛选条件变化
- 版本切换
- 表格重渲染后立即 hydration

不需要很大，建议：

- `120ms ~ 250ms`

目的不是降低功能响应，而是减少连续重绘造成的 hydration 抢占。

#### 方案 4：在 hydrate 完成后再做一次“未加载 slot 补扫”

推荐在容器 hydrate 完成后，再检查一次：

- 是否仍然存在 `.zt-bug-slot:not([data-zt-loaded])`

如果有，说明中途 DOM 有变更或有 slot 漏掉，可以再补一次短延迟重试。

这样能提升“最终一致性”。

#### 方案 5：将 hydration 和列表渲染显式分层

建议把流程明确拆成两步：

1. 本地数据渲染 DOM
2. DOM 稳定后触发禅道 hydration

推荐做法：

- 列表 render 完成后，使用 `requestAnimationFrame` 或微短延迟再调用 `hydrateContainer`

这样能降低“旧 DOM 尚未完全替换、新 DOM 尚未稳定时就发起 hydration”的概率。

---

### 5. 方案优先级建议

优先级从高到低建议如下：

1. 改 hydrator 的并发模型：全局 abort → 容器级 abort
2. 改 pending 策略：直接跳过 → 最新请求生效
3. 增加 render 后二次补扫
4. 增加轻量 debounce
5. 再考虑更进一步的缓存和增量更新优化

前两项是必须改的，后两项是稳定性增强。

## 三、推荐给 AI 的执行方向

如果后续要让 AI 实施，建议提示词明确要求：

1. 不重写 mine/retest/overall-test 业务逻辑，只重构页面容器层级
2. 一级导航只保留“我的工作台”，内部增加 3 个子页面切换器
3. 使用 CSS 横向 track + translateX 实现左右滑动动画
4. 原加载函数 `loadMyWorkbench`、`loadRetest`、`loadOverallTest` 保持复用
5. 修复 `frontend/js/zentao-hydrator.js` 的并发控制，不再使用全局 `_activeAbort` 抢占所有容器
6. 同一容器的新请求必须覆盖旧请求，不能简单 return 跳过
7. render 完成后对未加载 slot 做补扫，保证最终状态稳定显示

## 四、结论

### 需求 1：统一工作台

不是简单改文案，而是导航层级重构。

最稳的做法是：

- 保留原三个模块逻辑不动
- 新建一个工作台父容器
- 把三个模块变成该父容器下的子页面
- 用 track + translateX 做左右滑动动画

### 需求 2：禅道状态加载不稳定

根因不在筛选本身，而在 hydrator 的并发控制策略。

当前问题本质是：

- 全局 abort 抢占
- pending 容器直接跳过
- 高频重绘下，最新 DOM 没能拿到稳定 hydration

最核心的修复方向是：

- 改成容器级并发控制
- 只让最新请求生效
- 对漏掉的 slot 做补扫
