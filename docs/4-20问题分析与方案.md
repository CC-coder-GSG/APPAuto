## 问题 1　新建 Bug 报错 "禅道创建Bug失败: Expecting value: line 1 column 1 (char 0)"

### 现象

在"整体测试"页新建禅道 Bug 时，前端直接报出 `Expecting value: line 1 column 1 (char 0)`。

### 根因

这是 Python `json.JSONDecodeError` 的经典信息：对空字符串调用 `json.loads("")` 就会得到这条错误。
追到源头：

- `app/api/routes/zentao_bug_actions.py:249` 调用 `client.create_bug(body)`
- `app/services/zentao_client_service.py:266` → `self.post("bugs", data)`
- `app/services/zentao_client_service.py:111-123` 的 `post()`：

  ```python
  resp = httpx.post(url, json=body or {}, headers=self._headers(), timeout=_DEFAULT_TIMEOUT)
  if resp.status_code not in (200, 201):
      raise ZentaoAPIError(resp.status_code, resp.text[:500])
  return resp.json()          # ← 这里在 body 为空时抛 JSONDecodeError
  ```

  若禅道返回 201/200 + **空 body**，或返回 HTML（比如 PHP Warning 页面），`resp.json()` 会抛出 `Expecting value: ...`，被外层 `except Exception` 转为 `ZentaoAPIError(0, str(e))`，再被路由转换为 `HTTPException(status_code=502, detail="禅道创建Bug失败: Expecting value: ...")`。

- 另外一个可疑点：当前使用的 URL 是 `POST /api.php/v1/bugs`，而禅道官方 REST v1 创建 Bug 的标准路径是 **`POST /api.php/v1/products/{productID}/bugs`**（产品维度）。部分禅道版本对顶层 `/bugs` POST 不返回 JSON，或者直接 404，但路由器回落到别的页面时仍可能返回 200 + 空 body（取决于禅道版本/插件）。

### 解决方案（推荐组合）

**方案 A（必改）：容错空 body + 非 JSON 响应**

把 `ZentaoClient.post/put` 改成：

```python
text = (resp.text or "").strip()
if not text:
    return {"message": "success"}
try:
    return resp.json()
except ValueError:
    if "Fatal error" in text or "fatal error" in text:
        raise ZentaoAPIError(500, "禅道服务器内部错误（PHP Fatal Error）")
    # 对创建接口常见是返回 "bugID=xxx" 这样的简单文本，尝试从文本解析
    m = re.search(r'(?:bugID|id)[=:"\s]*(\d+)', text)
    if m:
        return {"id": int(m.group(1))}
    raise ZentaoAPIError(502, f"禅道返回了非 JSON 响应: {text[:200]}")
```

同时在 `create_zentao_bug` 路由里改成：只要 `bug_data.get("id")` 非空即可认为成功；`result` 为 `{"message":"success"}` 时回落到"再查一次 product 的 bug 列表/最大 id"（兜底可选）。

**方案 B（推荐同时做）：使用产品维度的创建路径**

把 `ZentaoClient.create_bug` 改为：

```python
def create_bug(self, product_id: int, data: dict) -> dict | None:
    body = {k: v for k, v in data.items() if k != "product"}
    return self.post(f"products/{product_id}/bugs", body)
```

路由层对应调整：把 `product` 从 body 里拆出，放进 URL。

这样同时收敛了"路径不一致/返回格式不确定"两类风险。

### 验证方式

用 chenwenbo 账号在整体测试页创建一个 Bug，预期：
- 成功时收到"禅道Bug #{id} 创建成功"
- 真失败时返回禅道可读的错误信息（而不是 JSONDecodeError）

## 问题 2　流转记录里的内嵌图片仍不显示（例：Bug b#29155）

### 现象

打开 Bug 预览弹窗，"复现步骤"里的截图能显示，但"流转记录"（actions）里 comment 中的嵌入截图显示为破图。

### 根因

后端在 `app/api/routes/zentao_bug_actions.py:364-380` 对预览做 URL 重写时，只覆盖了两个字段：

```python
if preview.get("steps"):
    preview["steps"] = _FILE_URL_RE.sub(lambda m: f"/zentao/files/{m.group(1)}", preview["steps"])

for f in preview.get("files") or []:
    ...  # files 列表里的 url
```

**没有处理 `preview["actions"][i]["comment"]` 里的 `file-read-*` / `file-download-*` URL。**

前端 `frontend/js/tabs/overall-test.js:922-935` 的 `_loadProxyImages` 只替换 `img[src^="/zentao/files/"]`，而 comment 里的原始 URL 形如 `http://192.168.2.148:81/zentao/file-read-12345.png`，浏览器直接请求禅道服务器不带 Token → 失败。

### 解决方案

**一行式修复**：在 `zentao_bug_actions.py` 的 preview 处理里，把同一个正则对 actions 也跑一遍：

```python
_FILE_URL_RE = re.compile(r'(?:https?://)?[^"\'>\s]*/file-(?:read|download)-(\d+)\.[a-zA-Z0-9]+')

if preview.get("steps"):
    preview["steps"] = _FILE_URL_RE.sub(lambda m: f"/zentao/files/{m.group(1)}", preview["steps"])

for act in preview.get("actions") or []:
    if act.get("comment"):
        act["comment"] = _FILE_URL_RE.sub(lambda m: f"/zentao/files/{m.group(1)}", act["comment"])

for f in preview.get("files") or []: ...
```

（建议抽成 `_rewrite_zentao_file_urls(html)` 工具函数，避免三处重复的 lambda。）

前端 `_loadProxyImages` 已经会把所有 `img[src^="/zentao/files/"]` 用 fetch+blob 懒加载，无需前端改动。

### 附加建议

- 若 action.comment 里有 `<a href="/zentao/file-download-xxx">` 这种点击下载链接，正则会顺带替换，`/zentao/files/{id}` 代理返回原文件即可，无需再单独处理。
- 若发现 comment 还有其它隐藏附件（比如 `file-preview-*`），可扩展正则：`file-(?:read|download|preview)-`。

### 验证方式

打开 b#29155，确认"流转记录"里的截图能够显示。

## 问题 3　创建 Bug 选中"执行"后，小版本候选仍是全量（未按执行过滤）

### 现象

在新建 Bug 弹窗选了某个执行，期望"影响版本"下拉只出现该执行绑定的 build；实际依然是该产品下的全部 builds。

### 根因

`app/api/routes/zentao_bug_actions.py:181-199` 的处理逻辑：

```python
meta = client.get_create_bug_meta(product_ids[0], selected_execution_id or 0)
...
builds = _normalize_meta_options(meta.get("builds"))  # 禅道 bug-create 页返回的是整个产品的 builds
...
if selected_execution_id and builds:
    execution_build_ids = set(client.get_execution_build_ids(selected_execution_id))
    if execution_build_ids:
        filtered_builds = {...}
        if filtered_builds:
            builds = filtered_builds
```

`client.get_execution_build_ids(execution_id)`（`app/services/zentao_client_service.py:319-339`）使用 `GET /api.php/v1/executions/{id}` 的根对象中的 `build/builds/openedBuild/openedBuilds` 字段。**禅道 v1 API 的执行详情通常不把 build 列表放在这里**，所以返回空列表，`execution_build_ids` 为空 → 不过滤 → 仍返回全量。

### 解决方案

切换到已经在别处验证可用的正确接口 —— **`GET /api.php/v1/executions/{id}/builds`**。
`app/services/overall_test_service.py:565` 和 `app/services/zentao_version_sync_service.py:176` 已在使用该路径，证明该数据源是可靠的。

```python
def get_execution_build_ids(self, execution_id: int) -> list[str]:
    try:
        resp = self.get(f"executions/{execution_id}/builds", params={"limit": 500})
        if not resp:
            return []
        rows = resp.get("builds") if isinstance(resp, dict) else []
        if not isinstance(rows, list):
            return []
        ids: list[str] = []
        for r in rows:
            if isinstance(r, dict) and r.get("id"):
                ids.append(str(r["id"]))
        return list(dict.fromkeys(ids))
    except Exception:
        return []
```

同时保留一个兜底：如果 `executions/{id}/builds` 也返回空（较旧的禅道版本），才回退到旧逻辑；否则严格用新接口结果过滤。

### 前端联动已就绪

`onS5CreateBugExecutionChange()`（`frontend/js/tabs/overall-test.js:1529`）已经在执行变化时重新请求 create-meta；只要后端返回过滤后的 builds，前端自动生效。

### 验证方式

在创建 Bug 弹窗连续切换不同执行，观察"影响版本"下拉随之刷新，候选数明显变少且只包含该执行绑定的 build。

## 问题 4　"复现步骤"不能粘贴/插入图片

### 现象

禅道原生 create-bug 页支持直接粘贴截图进复现步骤；我们用的是原生 `<textarea>`，只接受纯文本，粘贴截图时图片被丢弃。

### 根因

`frontend/index.html:1437`

```html
<textarea id="s5CreateBugSteps" placeholder="..." style="min-height:80px;"></textarea>
```

HTML `<textarea>` 本身不支持 HTML/图片；剪贴板里的图片会被浏览器直接忽略。

### 解决方案（分层）

推荐"**contenteditable + 服务端代理上传**"方案，分三步：

1. **前端**：把 `<textarea>` 换成 `<div contenteditable="true">` 或集成一个极简富文本编辑器；
   - 绑定 `paste` 事件：遍历 `event.clipboardData.items`，遇到 `type.startsWith("image/")` 的项
   - 把 Blob 通过 `FormData` 上传到新的后端端点 `POST /zentao/bugs/upload-inline-image`
   - 拿到后端返回的代理 URL（例如 `/zentao/files/{file_id}`）后 `document.execCommand('insertHTML', ...)` 插入 `<img>`
2. **后端新增** `POST /zentao/bugs/upload-inline-image`：
   - 接收二进制 → 用用户的 Token 调禅道 `POST /api.php/v1/files?objectType=bug&objectID=0`（或产品维度 `products/{pid}/files`，具体要查禅道版本）
   - 禅道成功后返回 `file_id`
   - 本地响应 `{file_id, proxy_url: "/zentao/files/{file_id}"}`
3. **提交时**：`submitS5CreateZentaoBug` 把 contenteditable 的 `innerHTML` 作为 `steps` 发给后端；`_format_steps_html`（`zentao_bug_actions.py:812`）已能识别 HTML（含 `<p>/<br>/<img>` 等），直接透传，不会二次包装。

### 关键细节与风险

- **objectType/objectID 问题**：禅道的 file 上传需要关联对象。Bug 还没创建 → `objectID=0`。需要在 Bug 创建成功后，后端再调一次 `files` 的改主接口把 `objectID` 绑到新 Bug。如果这一步省略，附件仍挂在临时对象上，禅道界面可能显示"无附件"。
- **代理 URL vs 原始 URL**：内联 `<img src="/zentao/files/{id}">` 对 OmniQA 用户能显示，但 **提交到禅道时 steps 里也是 `/zentao/files/{id}`**，禅道自己看不懂这个路径。
  解决：提交前把 `/zentao/files/{id}` 替换回 `{base_url}/file-read-{id}.png` 这种禅道能识别的形式（和预览时的正则互为反向操作）。
- **兼容最小改动方案**：如果觉得代理上传太重，可做简化版 —— 粘贴图片时提示"请先上传到禅道附件"，仅支持复现步骤文字，图片走附件区。但这其实和现状区别不大，体验不达标。

建议先做完整版。

### 验证方式

创建 Bug 时，截图 → Ctrl+V 进复现步骤 → 图片出现在编辑区 → 提交后到禅道 bug-view 页确认图片内嵌显示。

## 问题 5　新建 Bug 复现步骤没有"模板预填"（禅道默认有）

### 现象

禅道原生创建 Bug 页的复现步骤会预填：
```
[步骤]
1.
2.
3.
[结果]

[期望]

```
方便用户分段填写。我们的输入框是空的。

### 根因

`frontend/index.html:1437` 只给了 placeholder，没有 `value`。
`openS5CreateZentaoBugModal()`（`frontend/js/tabs/overall-test.js:1496`）初始化时也没设模板。

### 解决方案

**前端**：在 `_resetS5CreateBugForm()` 或 `openS5CreateZentaoBugModal()` 里，把步骤输入框预填为（若切换成 contenteditable，则预填等效 HTML）：

```
[步骤]
1.
2.
3.

[结果]


[期望]


```

**后端 `_format_steps_html`（`zentao_bug_actions.py:812`）需要去重**：现在的实现对于"不含 HTML 标签的纯文本"会二次加上 `<p>[步骤]</p>...<p>[结果]</p>...<p>[期望]</p>`，导致用户已经写好的模板再被套一层。修正：

```python
def _format_steps_html(text: str) -> str:
    content = (text or "").strip()
    if not content:
        return ""
    # 已经是 HTML：透传
    if any(tag in content.lower() for tag in ("<p", "<br", "<div", "<ol", "<ul", "<li", "<img")):
        return content
    # 纯文本但用户已写了 [步骤]/[结果]/[期望] 模板：保留结构，只把换行转 <br>
    if "[步骤]" in content or "[结果]" in content or "[期望]" in content:
        return content.replace("\r\n", "\n").replace("\n", "<br>")
    # 纯步骤文字：保持现在的包装行为
    lines = [line.strip() for line in content.replace("\r\n", "\n").split("\n") if line.strip()]
    return f"<p>[步骤]</p><p>{'<br>'.join(lines)}</p><p>[结果]</p><p></p><p>[期望]</p><p></p>"
```

### 与问题 4 的配合

如果问题 4 采用 contenteditable 方案，这里预填的就是 HTML 形式 `<p>[步骤]</p><p>1.</p>...`，`_format_steps_html` 会走 "已经是 HTML" 分支直接透传。

### 验证方式

打开创建 Bug 弹窗，步骤框已显示三段模板；写完提交，禅道 bug-view 页看到结构化的 [步骤]/[结果]/[期望] 分段。

## 问题 6　"复现步骤"输入框太小

### 现象

`min-height:80px` 太小，写两行就要拖动。用户希望能更大，最好支持自定义。

### 根因

`frontend/index.html:1437` 写死 `min-height:80px; resize:vertical;`。

### 解决方案

三层递进方案，任选：

- **方案 a（最小改动）**：把 `min-height` 提到 240px 左右，同时弹窗内容区从 `width:min(760px,96vw)` 提到 `min(900px,96vw)`；依赖 `resize: vertical` 让用户手动拖大。
- **方案 b（推荐）**：提供"展开全屏"按钮，点一下把整个复现步骤区域切到占满视口（position:fixed + 点外部返回），提交或关闭时收回。这种交互 Zentao 也做过。
- **方案 c（最彻底）**：把整个"新建禅道 Bug"弹窗自身变得可拖/可缩放（拖右下角）。实现上最麻烦，用户价值其实不如方案 b 直接。

建议方案 a + 方案 b 组合：
- 默认 240–320px 高度（够写 10 行左右）
- 步骤框右上角加一个"⛶ 放大"按钮
- 放大态是一个新的全屏浮层 contenteditable / textarea（共享同一个 value）

如果采用问题 4 的 contenteditable，这个"放大"按钮很好接。

### 验证方式

默认打开弹窗，步骤框已有足够空间；点"放大"后占据视口中央大面积，再点"收起"返回原位；输入内容在两种态之间保持一致。

## 问题 7　弹窗点外部区域不能关闭

### 现象

"新建禅道 Bug"、"重新激活"、"重新指派" 三个弹窗点外部遮罩不关闭，只能点右上角"✕ 关闭"。

```html
<div id="zentaoBugPreviewModal" onclick="closeZentaoBugPreview()" ...>

已经正确：外层遮罩负责关闭，内层 `stopPropagation` 防止点到卡片时关闭。

     onclick="closeS5CreateZentaoBugModal()"
     style="position:fixed; inset:0; ...">
  <div onclick="event.stopPropagation()"
       style="width:min(760px, 96vw); ...">
    ...
  </div>
</div>
```

同样 pattern 改 `s5ReactivateModal` / `s5AssignModal`。

### 可选增强

同时支持 `Esc` 关闭：在 `openS5*Modal()` 里绑定 `document.addEventListener('keydown', escHandler)`，`closeS5*Modal()` 里解绑。这是 Zentao 也没做到的 UX，但实现成本只多几行。

### 验证方式

打开每个弹窗，点遮罩 → 弹窗关闭；点弹窗内部 → 不关闭；按 Esc → 关闭。

## 问题 8　"重新激活"弹窗的两处问题

### 8.1 重新激活时"影响版本"仍是全量，未按该 Bug 所在执行过滤

#### 根因

`openS5ReactivateModal`（`overall-test.js:1206-1232`）调用 `/zentao/bugs/{ztId}/action-meta?action=activate`，后端走 `app/api/routes/zentao_bug_actions.py:412-477` 的 `get_bug_action_meta`，从禅道 `bug-activate-{id}.json` 页面取 `users/builds` —— 返回的是该产品下所有的 builds，没有按 Bug 所在执行做过滤。

#### 解决方案

在 `get_bug_action_meta` 路由返回之前，拿到 Bug 的执行信息并做过滤：

1. `bug-activate-{id}.json` 返回的 payload 里通常带 `bug.execution` 字段（即原始执行 id）
2. 若存在：调用和问题 3 同样的 `client.get_execution_build_ids(execution_id)`（已修正为 `executions/{id}/builds`），与 `builds` 做交集
3. 若交集非空：替换 `builds`
4. 若交集为空（执行没绑定 build 或旧版本 API）：保持全量，避免误删（给用户留后手）

代码骨架：

```python
bug_exec = None
if isinstance(bug_raw, dict):
    execution_raw = bug_raw.get("execution")
    if isinstance(execution_raw, dict):
        bug_exec = execution_raw.get("id")
    elif execution_raw:
        try:
            bug_exec = int(execution_raw)
        except (TypeError, ValueError):
            bug_exec = None

if bug_exec and builds:
    exec_build_ids = set(client.get_execution_build_ids(int(bug_exec)))
    if exec_build_ids:
        filtered = {bid: name for bid, name in builds.items() if bid in exec_build_ids}
        if filtered:
            builds = filtered

return {"users": users, "builds": builds, "current_assigned": current_assigned,
        "execution_id": bug_exec}  # 把 execution_id 也回传，后续可能用到
```

### 8.2 "取消闭环确认"应触发"重新激活"，否则不允许取消

#### 现状

`saveS5(id)`（`overall-test.js:551`）行为：
- `done=true` 且是禅道 Bug：调 `/zentao/bugs/{id}/close` 闭环
- `done=false`：**直接保存 `test_done=false`**，**不在禅道里做任何事**

这就导致：用户取消本地的闭环勾选后，禅道里这个 Bug 仍是 `closed` 状态，和本地数据不一致。

#### 用户预期

用户在文档里给出的完整逻辑：
> 如果某人取消闭环确认且 bug 是已关闭状态（闭环之后会直接关闭 bug 所以理论上这里应该一定是已关闭状态，可以查看一下是否有其他情况），那么需求触发重新激活功能；如果没有重新激活那么不允许取消闭环确认。

并附问：**是否存在除"已关闭"外的其它状态？**

#### 其它可能状态的回答

理论上如果闭环仅走 `/zentao/bugs/{id}/close`，一定跳成 closed。但实际会有边界：
- 用户闭环失败（禅道 close 报错）但本地前端仍把 `test_done` 落到数据库（当前 `saveS5` 里 `return` 在抛错前，所以正常不会）—— 已有防护。
- 外部直接在禅道把 Bug 改成 active/resolved 后，本地 `zentao_live_status` 在下次同步前还是 closed —— 这段窗口内取消闭环就面临"本地以为 closed，实际已 active"的情况。
- `zentao_deleted=True`（禅道里删了）的 Bug：不应允许激活，应给硬拦截。

所以结论：**不止 closed 一种**。建议以"**最新实时状态**"为准（而不是本地缓存的 `zentao_live_status`）。

#### 解决方案

在 `saveS5` 里检测 "由 done=true 变为 done=false 且是禅道 Bug" 的分支，然后：

```js
if (isZentaoBug && !done && bug.closed) {
    // 需要重新激活。拉取最新状态。
    const detail = await (await api(`/zentao/bugs/${ztId}/detail-status`)).json();
    // detail-status 返回 { live_status, execution_id } —— 新增轻量端点
    if (detail.live_status === 'closed') {
        // 打开重新激活弹窗（注入"激活成功后再继续保存 test_done=false"的回调）
        const ok = await openS5ReactivateModalAsync(id, ztId);   // Promise 化
        if (!ok) {
            // 用户取消或激活失败：回滚勾选框，不保存
            document.getElementById('done_' + id).checked = true;
            window.showMessage('未完成重新激活，已取消"取消闭环"操作', 'error');
            return;
        }
        // 激活成功后继续走下方的本地保存
    } else if (detail.live_status === 'active' || detail.live_status === 'resolved') {
        // 禅道已不是 closed（可能外部改了）：提示一下就直接允许取消闭环
        window.showMessage('禅道中该 Bug 已非"已关闭"状态，直接同步本地', 'info');
    } else {
        // 未知状态 / 删除：拦截
        window.showMessage('无法判断禅道 Bug 当前状态，请稍后再试', 'error');
        return;
    }
}
```

改造点：
1. **新增 API** `GET /zentao/bugs/{zt_id}/live-status`（轻量，只拉状态 & execution）；避免直接调完整 preview。
2. **把 `openS5ReactivateModal` 改造成支持回调/Promise**：激活成功后解析 `true`，取消/失败解析 `false`。
3. **UI 互斥**：在激活弹窗提交之前，把外层的 done checkbox 禁用，避免二次触发。

### 验证方式

- 在整体测试页，对一个"已闭环+禅道已关闭"的 Bug 取消勾选 → 出现重新激活弹窗 → 选指派人 → 确认 → 禅道状态变 active + 本地 `test_done=false` 成功保存。
- 弹窗里点取消 → 勾选被自动回滚，本地和禅道都无变化。
- 手工在禅道把该 Bug 改成 active 后，再在本系统取消勾选 → 直接提示"禅道已非已关闭"并允许保存；不打开激活弹窗。
