# 数据库锁与连接池耗尽：第一、二步修复

## 现场证据

服务器日志确认最终测试提交和登录更新会话均出现 SQLite `database is locked`，并出现 `QueuePool size 5 overflow 10 timeout 30`。禅道同时存在超时及连接重置。不能仅由异常堆栈认定最初持锁者。

## 本次改动

- 用例全量/增量同步：先读取列表和必要详情，再落库。修复先 flush 新记录、随后在同一写事务中等待远程详情的路径。全量保持分批提交，增量按产品提交。
- 任务镜像：按执行版本提交；失败立即回滚，再继续下一个版本，避免前一个版本的写事务跨越下一次网络请求。
- 需求/Bug 标签批量读取：获得用户和客户端信息后释放干净的读事务，等待禅道时归还连接；Token 刷新后重试也执行同样边界。
- Token 刷新、任务状态查询等关键路径在没有待保存对象时释放读事务。存在待保存对象时不会隐式提交这些变更。
- 最终测试：新增记录延后到禅道任务确认后的本地保存阶段才加入会话，避免被内部认证或任务同步的提交提前写入。
- 批量同步统一使用进程内单名额，覆盖 Bug、用例、任务镜像及定时全量/增量任务。嵌套同步复用名额；并发请求立即返回 409，不持连接排队。保留原数据库资源锁。
- 产品 Bug 拉取串行化，避免在线程池中的 Token 刷新跨线程操作同一个 SQLAlchemy Session。
- 同步异常先 rollback，再释放数据库业务锁，避免释放锁时顺带提交半成品。
- 请求异常显式回滚；连接占用超过 5 秒归还时记录耗时和池状态，不记录 SQL 参数。数据库锁和池超时返回 503 与核对结果提示，不自动重放业务写入。

## 验证

204 项定向测试通过。新增验证包括：单连接池下读连接归还、待保存对象不被隐式提交、同步拒绝重叠且失败释放名额、用例详情阶段无活跃事务、最终测试远程联动前没有待插入最终测试记录。

## Windows 服务上线步骤

1. 维护窗口停止服务，保存当前代码版本；停止后备份部署目录中的实际数据库和相关文件。
2. 部署代码，再启动服务。本次不包含数据库结构迁移，不需要手工改表或扩大连接池。
3. 初次验证以一个应用进程为准，确认没有另一套服务或手工启动的进程同时执行后台同步。此次全局同步名额仅在单进程内有效；多进程之间不同资源的同步仍可能并行。
4. 验证登录、V4.0.5.0 最终测试完成/取消、工时操作；同时触发同步，确认重复同步提示稍后再试且正常业务可继续。
5. 观察 stderr 中 `database is locked`、`QueuePool`、`database request failed` 和 `db connection held`。新连接日志是在归还时记录，不能代替正在占用连接的实时监控。
6. 若上线后依然出现长占用，依据对应请求和同步日志继续追踪其余禅道操作路径；不要仅延长超时或增加服务进程。

代码回归不能证明现场故障已消除。此次没有对服务器执行部署、重启或业务状态变更，生产确认需在上线后进行。
