# Bugly 问题中心：使用与部署说明

本次实现文件导入与受限外部浏览。原有 Bugly 插件继续导出 JSON/CSV；测试平台接收文件，不要求外部人员登录 Bugly。

## 入口

- 内部管理页：平台地址后加 `/bugly`，或从平台导航点击“Bugly 问题中心”。
- 外部浏览页：平台地址后加 `/bugly/external`，外部账号登录后自动进入。
- 未登录时跳转平台登录页；外部账号无法调用内部管理、用户列表、全局事件流等接口。

## 首次配置

1. 管理员进入“应用管理”，填写名称、来源站点、平台、来源时区，建议同时填写包名和 Bugly App ID。
2. 每个 Bugly 应用建立独立数据空间；来自不同 Bugly 站点、不同系统平台的应用分别建档。
3. 来源站点填写插件采集页面实际主机名，例如 `bugly.qq.com`，不要填写 URL 路径。来源时区用于解释没有时区的 Bugly 时间，默认 `Asia/Shanghai`。
4. 进入“权限管理”，为内部用户分配整个应用或指定问题的权限。保存授权时会为内部用户增加 Bugly 页面入口；业务数据权限仍以模块授权为准。

内部用户可以分别获得只读查看、维护、查看原始资料、审核发布权限；有指定问题维护权限的用户可以在问题详情新增上报。应用级新增问题和导入文件需要整个应用的维护权限。

## 新增与查看

- “新增问题”填写应用、标题和可选 Bugly 编号。没有真实编号可以留空。
- 在详情“新增上报”填写版本、设备、发生时间及堆栈，没有上报编号时留空。
- 列表可按应用、版本、设备、处理状态、发生时间和关键词查询；查看方式可切换为“按问题聚合”和“逐条上报”。
- 问题详情支持上报搜索、分页、堆栈定位/复制/换行/展开及现场字段查看。
- 有原始资料权限的内部人员可查看原始文本、诊断和最近 50 次上报修订。
- 编辑问题可以指定负责人、维护内部分析及对外说明、归档或恢复问题。归档会撤回对外发布。

统计口径是已导入数据，不代表 Bugly 原站的全量问题或全量上报。发生时间和采集时间分开保存，页面按浏览者所在时区显示可解析时间；无法解析的发生时间保留原文。

## 导入

1. 插件在 Bugly 问题页点击“采集并导出”，得到 JSON；也可导出 CSV。
2. 平台点击“导入文件”，选择对应应用及文件。每次最多选择 10 个文件；每文件最多 20 MB、2,000 条记录。
3. JSON 完整兼容当前插件 `schemaVersion=1`。CSV 支持 BOM、引号、多行堆栈及动态 `列表.*` / `详情.*` 列。
4. 问题编号未识别时，可从归属问题下拉框选择一个现有问题；默认按文件编号自动识别。
5. 检查预计新增、更新、跳过和无效条目，点击“确认导入有效记录”。无效行保留原因；原插件的采集失败项保留在批次记录，不生成成功上报。
6. 在“导入记录”查看最近 50 次任务的校验与实际处理结果。预览保存 30 分钟，超时后重新上传。

同应用同问题同上报编号不会重复插入。不同内容形成修订；未提供/空白采集字段不擦除已有资料，人工分析、负责人及状态不被导入覆盖。确认后再次点击返回同一结果；如果预览后数据已被其他导入修改，返回冲突，需重新预览。

如果先同时预览多个包含相同上报的文件，第一个确认可能使后续文件的预览失效。发生冲突时重新预览剩余文件后确认，以免按旧预览覆盖最新堆栈。

包名或来源站点与所选应用明确不一致的行会提示无效，先核对应用配置。堆栈为空、仅有 fallback 或采集等待超时会提示检查，仍可按有效记录保存。

## 外部浏览

1. 管理员在“权限管理”创建独立外部账号，设置初始密码和可选账号有效期。
2. 分配“整个应用”或“指定问题”的只读权限，可设置授权有效期。外部账号不能获得维护、原始资料或发布权限。
3. 有发布权的人员进入问题详情，点击“对外预览与发布”。系统生成脱敏候选内容，可以继续编辑标题、说明、设备字段和堆栈，也可取消部分上报。
4. 检查完成后发布，外部账号可查看该发布快照。标题、内部分析和原始数据的后续修改不会直接改变外部页面。
5. 新增/导入/更新后如需对外展示，重新预览发布。撤回、归档、撤销授权及到期会阻止后续访问。

外部响应不包含内部分析、用户 ID 字段、采集诊断、原始文本和 Bugly 链接。自动脱敏辅助处理常见 Token、已知用户 ID、URL、IP 和路径；自由文本仍需发布人员人工检查。

“外部账号”区域可调整到期时间、停用/启用账号、重置密码。停用和有效期调整会撤销原登录会话。页面响应使用 `Cache-Control: no-store`。

账号权限无法收回访问者此前自行复制或保存的内容。免登录分享链接和插件直接上传属于后续扩展，本次未增加。

## 升级与运行

沿用平台现有运行方式和依赖，无需引入新前端框架。

依赖清单增加 `tzdata`，用于 Windows 上的 IANA 来源时区解析；部署时按原流程执行 `pip install -r requirements.txt`。

1. 部署本次代码后按现有流程重启平台（开发环境使用 `.venv\Scripts\python.exe -m uvicorn app.main:app --reload`）。
2. 启动初始化会检测旧用户表，并在首次 Bugly 升级前通过 SQLite backup API 自动备份现有数据库及已提交 WAL 数据。备份保存在数据库旁的 `bugly-backups` 目录。
3. 自动创建 Bugly 数据表，并给用户表增加 `account_type`、`is_active`、`expires_at`。原用户默认保留为启用的内部用户。重复启动不会重复备份或重复添加列。
4. 备份失败会中止升级，需确保服务账号有数据库与备份目录权限，再重试。
5. 在真实环境配置应用、用当前插件实际导出文件试导入，再分配外部账号。

本次开发验证使用独立数据库，没有导入真实 Bugly 数据、没有修改真实业务数据库，也没有发布公网地址。

外网访问还需现有部署环境提供 HTTPS 域名或合作方网络入口。网关优先仅开放 `/bugly/external`、`/login`、所需静态资源、`/auth/token`、`/auth/me`、`/auth/password`、`/auth/logout` 以及 `/api/bugly/external/*`；禁止直接开放数据库备份目录。应用后端仍逐请求验证授权，不能以网关路径限制代替。
