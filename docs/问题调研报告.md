## 2. 总体结论

当前系统已经从“本地 Bug 台账”演进到了“本地缓存 + 禅道远端动作”模式，但还没有完全闭环，核心矛盾有四个：

1. 整体测试页已经接入了禅道同步和禅道动作，但前端排版和状态回写仍偏临时拼装，导致按钮跳动、关闭后位置变化、备注区域常驻展开。
2. 禅道数据虽然已经会写入本地数据库，但缓存层还不完整。当前只有版本级 5 分钟内存缓存，没有完整的“按 Bug 增量同步 + 后台异步刷新 + 最后同步时间可视化”方案。
3. 权限模型仍然是简单的 `admin / 非 admin` 二元判断，无法支撑“按 tab 页面配置权限”。
4. 报表中心和数据管理台目前统计口径仍然主要基于本地表，尚未把禅道实时状态、同步时间、删除状态、关闭备注等新增字段完整吸收进来。

建议把后续改造拆成 4 个阶段：

1. 修整体测试页交互和状态一致性。
2. 补完整缓存/增量同步体系。
3. 升级权限模型和任务分配台需求同步。
4. 再做报表中心、质量资产大盘和 AI 预留。

## 3. 分项调研

### 3.1 问题 1：点击下一页后页面会自动向下滑动

**现状**

翻页后会调用 `scrollS5ToolbarIntoView()`，内部直接执行 `scrollIntoView({ block: 'start', behavior: 'smooth' })`，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:49)。分页切换 `prevS5Page`、`nextS5Page`、`applyS5PageSize` 都会触发它，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:268)。

**结论**

这不是浏览器偶发行为，而是现有实现的明确设计。

**建议方案**

- 去掉自动滚动。
- 如果担心用户翻页后看不到表头，改成仅在“当前工具条不在视口内”时再平滑滚回顶部。
- 更稳的做法是只做 `scrollTop` 的最小修正，不使用 `scrollIntoView`，避免页面整体跳动。

**优先级**

高。改动小，收益直接。

### 3.2 问题 2：Bug 功能按钮同步前后位置会变化

**现状**

每行按钮是直接拼在 Bug 编号单元格里的，编辑、删除、指派、重新激活都通过字符串拼接生成，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:155)。按钮集合会随着是否是禅道 Bug、是否已关闭、是否显示他人记录而变化；同时闭环说明输入框也会插入在同一操作区，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:208)。

**根因**

- 同一列同时承载了：Bug 编号、来源、状态徽标、功能按钮、他人闭环记录。
- 不同状态下按钮数量不一致。
- 同步前后 `zentao_bug_url`、`zentao_bug_title`、`zentao_live_status` 补齐后，整列宽度和内容密度都会变化。

**建议方案**

- 重构 Stage5 行布局，拆成固定 4 区：
  - 左：Bug 编号与来源
  - 中：标题
  - 右上：固定操作栏
  - 右下：验证区
- 操作栏使用固定顺序和固定占位：
  - `编辑`
  - `删除`
  - `指派`
  - `重新激活`
- 对当前状态不可用的操作显示为禁用态，而不是直接消失。
- 他人闭环记录不要再塞进按钮区，独立放到折叠区域或“详情展开行”。

**优先级**

高。属于当前整体测试页最明显的交互问题之一。

### 3.3 问题 3：关闭 Bug 后位置发生变化，希望保持位置不变

**现状**

整体测试后端默认按 `updated_at desc, id desc` 倒序返回，见 [stage5_service.py](/E:/APPAUTO/APPAuto/app/services/stage5_service.py:84)。而关闭 Bug、编辑标题、指派、重新激活、同步禅道状态都会更新 `updated_at`，因此一旦操作成功，该 Bug 会被重新排序。

**结论**

这是当前排序规则直接导致的，不是前端渲染抖动。

**建议方案**

有两种方案：

- 方案 A：保持全局默认倒序，但本次操作后前端局部更新，不立即全量重载。
  - 优点：保留“最新变更在前”。
  - 缺点：排序语义与数据库最终顺序可能暂时不一致。
- 方案 B：整体测试页默认按 `created_at desc` 或 `bug_id desc` 固定排序。
  - 优点：关闭前后位置稳定。
  - 缺点：用户看不到最近更新排序。

更推荐折中方案：

- 默认排序改成稳定字段，如 `created_at desc, id desc`。
- 如果后续需要“最近有变化”，单独提供排序切换器，而不是把 `updated_at` 作为唯一默认排序。

### 3.4 问题 4：禅道已关闭 Bug 自动做闭环确认，并显示关闭备注

**现状**

当前本地闭环统计完全依赖 `BugStage5Record.test_done` 和 `BugTracking.closed`。提交闭环时，本地先保存记录，再调用禅道关闭接口，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:333)。后端聚合逻辑也只看本地闭环记录，见 [stage5_service.py](/E:/APPAUTO/APPAuto/app/services/stage5_service.py:178)。

`BugStage5Record` 目前没有“闭环说明”字段，见 [stage5.py](/E:/APPAUTO/APPAuto/app/models/stage5.py:11)。`BugTracking` 也没有“禅道关闭备注”或“禅道关闭者账号”字段，见 [bug.py](/E:/APPAUTO/APPAuto/app/models/bug.py:12)。

**结论**

这个需求能做，但不能只靠前端补显示，必须补数据模型。

**推荐方案**

新增两层同步：

1. 禅道关闭态回写层
   - 在版本 Bug 同步时，把禅道返回的：
     - `status`
     - `closedBy`
     - `closedDate`
     - `comment` 或关闭备注
     一并缓存到本地。
2. 本地闭环映射层
   - 在 Stage5 加载时，如果 Bug 的禅道状态已是 `closed`，尝试按“关闭者姓名/账号”映射到本地用户。
   - 若能映射到某个本地用户，则为该用户自动补一条“系统同步的闭环记录”。
   - 其他用户不自动打勾。

**统计口径建议**

- 已被禅道关闭的 Bug 应计入“已闭环”总数。
- 但页面上要区分：
  - `本地人工确认闭环`
  - `根据禅道关闭状态自动同步闭环`

**风险**

- 禅道关闭者显示名和本地用户显示名可能不完全一致。
- 更稳的映射方式应优先使用账号，再兜底显示名模糊匹配。

### 3.5 问题 5：已确认闭环的 Bug 卡片无法收起

**现状**

现在关闭说明输入框通过 `toggleS5CloseComment()` 控制显示隐藏，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:327)。但它本质上是插在行内的一个常驻 `textarea` 区块，不是折叠面板；已勾选闭环后默认会保持展开。

**结论**

这不是“没有收起逻辑”，而是当前设计根本没做“闭环详情折叠态”。

**建议方案**

- 把“闭环说明”从行内展开改成：
  - 小弹窗
  - 抽屉
  - 或 `details/summary` 折叠块
- 行内仅保留一行摘要：
  - `已闭环`
  - `关闭者`
  - `最后备注摘要`
- 点击“查看备注”再展开详情。

### 3.6 问题 6：确认“全部版本”的统计规则

**现状**

“全部版本”模式不是去禅道查全产品全量 Bug，而是只查询本地 `bug_tracking` 中、当前软件下所有大版本的记录，见 [stage5_service.py](/E:/APPAUTO/APPAuto/app/services/stage5_service.py:34)。

而且 Stage5 同步入口只支持“同步某一个具体大版本”，见 [stage5.py](/E:/APPAUTO/APPAuto/app/api/routes/stage5.py:47)。因此“全部版本”页看到的是：

- 所有已同步入本地库的大版本 Bug 汇总
- 不是禅道产品下的全量 Bug 汇总

**结论**

你看到“禅道很多，但全部版本只有一百多条”是符合当前实现的。

**建议方案**

- 明确产品定义：
  - `全部版本` = 当前软件下、本地已缓存的所有大版本 Bug 汇总
  - 不是禅道产品全量总 Bug
- 页面上加提示：
  - “全部版本统计基于本系统已同步入库的数据”
- 如果你后续真要做“禅道产品全量视图”，那应新增单独模式，不建议复用当前“全部版本”。

### 3.7 问题 7：同步慢，希望数据库缓存、后台同步、增量更新、显示最后同步时间

**现状**

当前已经有两层缓存/同步基础：

- 本地数据库缓存：
  - `BugTracking` 已有 `zentao_sync_status`、`zentao_sync_message`、`last_zentao_synced_at`、`zentao_live_status`、`zentao_deleted` 等字段，见 [bug.py](/E:/APPAUTO/APPAuto/app/models/bug.py:61)
- 版本级内存 TTL：
  - `_sync_cache` 记录 5 分钟内某大版本是否刚同步过，见 [stage5_service.py](/E:/APPAUTO/APPAuto/app/services/stage5_service.py:25)

但目前还不完整：

- `last_zentao_synced_at` 没有返回给 Stage5 前端展示。
- 版本级缓存还是内存态，不是可观测的同步任务。
- 每次同步仍然是“拉取该版本全部远端 Bug，再逐条 upsert”，见 [stage5_service.py](/E:/APPAUTO/APPAuto/app/services/stage5_service.py:262)。
- 当前页加载前会同步，仍在用户请求链路中，用户会感知等待。

**结论**

你希望的方向是正确的，而且当前模型字段已经为这个方案预留了一部分条件。

**推荐方案**

分成 3 层：

1. 页面读取层
   - 页面始终优先读本地数据库。
   - 前端显示 `last_zentao_synced_at`。
2. 后台刷新层
   - 用户打开页面后立即显示本地缓存。
   - 后台异步发起增量同步。
   - 同步完成后只刷新受影响的行。
3. 增量同步层
   - 不再每次都按版本全量 upsert。
   - 以 `zentao_bug_id` 为主键做差量：
     - 新增远端有、本地无
     - 更新标题、状态、关闭者、备注、指派人、更新时间
     - 删除/隐藏远端 `deleted=true`

**建议新增字段**

- `zentao_remote_updated_at`
- `zentao_closed_by_account`
- `zentao_closed_by_name`
- `zentao_close_comment`
- `zentao_assigned_to_account`
- `zentao_assigned_to_name`
- `last_zentao_checked_at`

**同步策略建议**

- 进入页面：直接返回本地
- 若本地上次同步超过阈值，如 60 秒或 120 秒：
  - 后台启动增量同步
- 用户主动点击“强制同步”：
  - 执行完整版本级校准

**性能重点**

- 保持当前 build 并发抓取思路，见 [stage5_service.py](/E:/APPAUTO/APPAuto/app/services/stage5_service.py:424)
- 把“同步”和“页面首屏返回”彻底拆开
- 用数据库记录同步水位，不再只依赖进程内 `_sync_cache`

### 3.8 问题 8：指派者列表加载不出来

**现状**

代码层面已经有候选人加载逻辑：

- 前端会调用 `/zentao/bugs/{id}/action-meta?action=activate|view`，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:546)
- 后端会从禅道页面 JSON 中解析 `users` 字典，见 [zentao_bug_actions.py](/E:/APPAUTO/APPAuto/app/api/routes/zentao_bug_actions.py:70)
- 前端再构造成带搜索框的下拉，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:554)

我之前已核验过：禅道网页使用的页面 JSON 本身就带 `users`，不需要依赖 `/api.php/v1/users`。

**推断根因**

这类“列表加载不出来”更可能有 4 种原因：

1. 当前用户没有可用禅道绑定，后端会直接返回空字典。
2. 页面 JSON 获取成功，但 `users` 被解析为空。
3. 前端搜索下拉已创建，但因为容器高度/样式问题看起来像没加载。
4. 当前行的 `zentao_bug_id` 未正确传入，导致 action-meta 请求取不到目标 Bug。

**建议排查方案**

- 在前端给 `action-meta` 请求结果增加临时日志或错误态提示。
- 对空 `users` 明确提示：
  - `未获取到可指派候选人`
  - `请检查禅道绑定/权限/目标 Bug 状态`
- 把当前请求到的候选人数显示在弹窗标题处，例如 `候选人 267 人`。

**实现建议**

- 指派和重新激活共用同一套“可搜索候选人选择器”。
- 搜索同时支持：
  - 账号
  - 显示名
  - 拼音首字母扩展匹配

### 3.9 问题 9：点击编辑按钮报错

**现状**

编辑按钮是通过内联 `onclick` 直接把标题字符串拼进 HTML 的，见 [stage5.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/stage5.js:190)。

**高概率根因**

这里最脆弱的点是：

- 标题里如果带引号、换行、HTML 实体、反斜杠
- 经过 `escapeHtml()` 和 `JSON.stringify()` 混合处理后
- 很容易让内联事件参数变形

尤其是禅道标题经常包含：

- 单引号
- 双引号
- 括号
- HTML 实体

**结论**

这个问题更像是“内联事件参数序列化不安全”，不是后端编辑接口本身有问题，因为后端 `PUT /zentao/bugs/{id}` 已经存在，见 [zentao_bug_actions.py](/E:/APPAUTO/APPAuto/app/api/routes/zentao_bug_actions.py:138)。

**建议方案**

- 不再把标题作为字符串拼进 `onclick`。
- 改成：
  - 按钮只带 `data-id`、`data-zt-id`
  - 标题从 DOM dataset 里取
  - 或点击后根据当前行状态对象取值

这是典型的前端事件绑定问题，修复优先级高。

### 3.11 问题 11：任务分配台需求应实时从禅道同步，并支持按 tab 授权

**现状**

任务分配台仍然完全依赖本地 `Requirement` 表，见 [requirements.py](/E:/APPAUTO/APPAuto/app/api/routes/requirements.py:104) 和 [assign.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/assign.js:110)。

权限方面更明显：

- 前端初始化时直接按 `currentUser.role === 'admin'` 控制 tab 显示，见 [index.html](/E:/APPAUTO/APPAuto/frontend/index.html:1471)
- 后端接口也大量直接 `ensure_admin(current_user)`，见 [users.py](/E:/APPAUTO/APPAuto/app/api/routes/users.py:42)、[admin.py](/E:/APPAUTO/APPAuto/app/api/routes/admin.py:111)
- 当前并不存在“tab 粒度权限表”

**结论**

这个需求分成两块，且都是结构性改造：

1. 需求同步：当前没有“选版本同步禅道需求”的服务
2. 权限升级：当前没有“按 tab 授权”的权限模型

**建议方案 A：需求同步**

- 新增“按版本同步禅道需求”服务
  - 输入：软件、大版本、可选项目/执行

### 3.12 问题 12：反馈页面“反馈概览”输入框高度明显不协调

### 3.13 问题 13：检查报表中心统计是否还能正常工作，并评估禅道可用统计接口

**现状**

报表中心主要依赖本地业务表统计，见 [reports.py](/E:/APPAUTO/APPAuto/app/api/routes/reports.py:10) 和 [report_service.py](/E:/APPAUTO/APPAuto/app/services/report_service.py:531)。

其中与本次改造最相关的点：

- 闭环 Bug 统计依赖本地 `BugStage5Record` 和 `BugTracking.closed`
- Bug 治理统计依赖本地 `BugTracking`
- 当前并没有把：
  - `zentao_live_status`
  - `last_zentao_synced_at`
  - `zentao_deleted`
  - 禅道关闭备注
  纳入报表口径

**结论**

如果后续引入“禅道关闭自动映射本地闭环”“禅道软删除”“增量同步时间”等机制，报表中心必须同步升级，否则统计会出现口径偏差。

**建议升级方向**

1. 报表继续以本地库为主
   - 不建议让报表页面实时打禅道 API
   - 报表最需要的是口径稳定，不是实时性
2. 新增同步维度
   - 最近同步时间
   - 禅道关闭态 vs 本地闭环态差异
   - 禅道已删但本地保留的 Bug 数量
3. 增加治理看板
   - `未同步超过 N 分钟的 Bug`
   - `禅道已关闭但本地无人确认的 Bug`
   - `本地已闭环但禅道未关闭的 Bug`

**关于禅道统计接口**

当前已确认可稳定使用的是对象级查询与动作接口。是否存在可直接复用的“报表中心统计接口”，目前没有在本项目代码中落地使用，也不建议把报表强绑定到禅道统计口径。

更合理的策略是：

- 禅道负责提供原始状态
- 本系统在本地二次建模形成自己的统计

### 3.14 问题 14：数据管理台“质量资产大盘”数据好像没有同步过来

**现状**

数据管理台当前读取 `/admin/data-overview`，返回的是本地数据库中的：

- 用户
- 版本
- 需求
- Bug

见 [admin.py](/E:/APPAUTO/APPAuto/app/api/routes/admin.py:110)。并没有主动从禅道补拉数据。

**结论**

“质量资产大盘没有同步过来”是准确判断。它现在只是本地数据浏览器。

**建议方案**

把数据管理台升级成“本地资产总览 + 禅道缓存视角”，重点补 3 类数据：

1. 版本资产
   - 展示 `zentao_execution_id`
   - 展示上次同步时间
2. 需求资产
   - 增加禅道需求来源、同步状态、最近同步时间
3. Bug 资产
   - 展示 `zentao_bug_id`
   - 展示 `zentao_live_status`
   - 展示 `zentao_deleted`
   - 展示 `last_zentao_synced_at`

**关键建议**

- 数据管理台不负责实时同步
- 它负责“看缓存质量”和“看资产完整度”

也就是说它应该成为：

- 同步状态监控台
- 数据追溯台
- 资产诊断台

### 3.15 问题 15：后期接入 AI，建议现在预留什么设计

**结论**

现在最值得提前预留的不是 UI，而是“可供 AI 安全调用的结构化能力”。

**建议预留 5 类能力**

1. 统一动作接口层
   - 把页面上的关键动作都沉淀成明确 API
   - 例如：
     - 查询版本
     - 查询需求
     - 查询 Bug
     - 关闭/激活/指派/删除 Bug
     - 提交反馈
2. 可审计的操作日志
   - AI 代操作必须有独立审计字段
   - 区分：
     - 用户手动操作
     - AI 建议
     - AI 自动执行
3. 权限隔离
   - AI 不应天然继承管理员权限
   - 应按功能域授权
4. 结构化上下文
   - 给 AI 提供稳定 JSON，而不是从 HTML 拼文本
   - 例如：
     - Bug 卡片 JSON
     - 需求进度 JSON
     - 同步状态 JSON
5. 异步任务机制
   - AI 触发的同步、统计、批量修复建议应进入任务队列
   - 不要长时间占住用户请求

**额外建议**

如果后面真要让 AI 参与测试管理，优先做这三类 AI 场景：

- 缺陷归类与优先级建议
- 闭环异常检测
- 报表自动解读

不要第一阶段就让 AI 直接做删除、关闭、批量改状态。
