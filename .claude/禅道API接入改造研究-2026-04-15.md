## 1. 结论先行

当前最合适的改造方向不是“把本地测试管理系统改造成禅道镜像系统”，而是：

1. 保留本地系统作为业务工作流主系统。
2. 保留 `Requirement / TestCase / BugTracking / Stage5 / FieldTest / Dispatch / Report` 这套本地闭环。
3. 把禅道改造成“实时详情层 + 外部事实源”。
4. 把现有浏览器插件同步链路从“主要展示数据来源”降级为“创建时上下文捕获 + 自动映射辅助”。
5. 前端直接调用禅道 API 在你当前环境里是可行的，而且我已经实际验证了 CORS、Token 和多类对象接口。

一句话总结：

> 本地系统继续管流程、归属、统计、闭环；禅道实时提供 Bug/需求/执行/版本/发布/用例等原始详情。

## 3. 禅道实例 API 实测结果

以下结果全部是我在 2026-04-15 对你给出的内网禅道实例实测得到的。

### 3.1 登录与 CORS

已实测成功：

- `GET /api.php` 返回 `{"error":"EMPTY_ENTRY"}`，说明入口存在
- `POST /api.php/v1/tokens` 成功返回 token
- `OPTIONS /api.php/v1/tokens` 返回 `204`
- `OPTIONS /api.php/v1/products/15/bugs` 返回 `204`
- 返回头包含：
  - `Access-Control-Allow-Origin: *`
  - `Access-Control-Allow-Headers: Origin,X-Requested-With,Content-Type,Accept,Authorization,Token,Referer,User-Agent`
  - `Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS,PATCH`

结论：

> 从浏览器直接调用禅道 v1 API 在你当前环境中是技术上可行的，不需要先做后端中转才能完成基础读取。

### 3.5 实测到的返回数据特点

#### Bug 详情够丰富

`GET /v1/bugs/{id}` 已确认可直接拿到：

- 基础字段：`title / status / severity / pri / type / deadline`
- 关联字段：`product / project / execution / plan / story / case`
- 展示字段：`steps / openedBuild / assignedTo / openedBy / resolution`
- 历史字段：`actions[]`

这足够支撑：

- 详情抽屉
- bug 标题/状态/指派人实时展示
- 历史动作展示
- 与需求/执行/版本的反向跳转

#### Story 详情也够支撑需求展示

`GET /v1/stories/{id}` 已确认可拿到：

- `title / status / stage / pri / estimate`
- `assignedTo / openedBy / reviewedBy`
- `plan / planTitle`
- `actions[]`

这可以支撑你系统里的“需求详情补充信息”。

#### Build / Release / TestTask 说明“版本相关信息”远比当前方案更丰富

实测表明：

- Build 可以拿到：构建名、日期、关联 Bug、关联 Story、builder、executionName、productName
- Release 可以拿到：发布名、发布日期、关联 Build、关联 Story、关联 Bug、发布说明
- TestTask 可以拿到：测试任务名、owner、build、execution、时间区间、状态

也就是说：

> 你后面不应该只考虑 Bug 和 Story，还应该把 Build / Release / TestTask 纳入“版本信息展示层”。

#### 同一对象在不同列表接口中的字段形态并不完全一致

我实测到了一个很重要的实现风险：

- `/products/{id}/bugs` 中 `openedBy / assignedTo` 可能是对象
- `/executions/{id}/bugs` 中同名字段可能是字符串
- `testcase` 列表中有的接口返回 `id = "case_21547"`，有的返回 `caseID = 21547`
- `/products/{id}/stories` 实测返回成功时状态码曾出现 `201`

结论：

> 你必须做统一的“前端禅道响应归一化层”，不能在页面里直接吃原始响应。

#### 实体 ID 不是全局唯一，必须按实体类型分别存

实际实例里同时存在：

- `product 134`
- `project 134`

因此不能只存一个通用 `zentao_id`，必须按对象类型分别存：

- `zentao_product_id`
- `zentao_project_id`
- `zentao_execution_id`
- `zentao_story_id`
- `zentao_bug_id`
- `zentao_case_id`
- `zentao_build_id`
- `zentao_release_id`
- `zentao_testtask_id`

## 4. 对比当前系统后，真正应该怎样改

## 4.1 总体原则

建议采用“四层结构”：

1. 本地业务层
   - 继续负责流程、归属、统计、消息、权限、闭环
2. 本地映射层
   - 只负责把本地对象锚定到禅道对象
3. 禅道实时读取层
   - 负责详情、状态、历史、版本信息实时获取
4. 展示适配层
   - 把禅道原始结构整理成你页面当前能直接消费的 shape

### 4.2 哪些东西必须继续留在本地

必须本地保留，不建议让禅道取代：

- Requirement 的负责人/复测人/完成状态
- TestCase 与 Requirement 的本地归属关系
- BugTracking 的 `source_type / source_ref / found_minor_version_id / fixed_minor_version_id / dispatched_to_id / is_retest_failed / closed / resolution`
- FieldTest / Stage5 / Dispatch / Report 的流程状态和结果
- SSE、企业微信通知、活动流、审计日志

原因很简单：

> 禅道能告诉你“对象是什么”，但不能替代你这套“测试运营流程”。

### 4.3 哪些东西不应该再长期镜像到本地

这些字段后续不应该继续做高频镜像主源：

- `zentao_bug_title`
- `zentao_bug_url`
- `zentao_product_name`
- `zentao_project_name`
- `zentao_execution_name`
- `zentao_requirement_name`
- `zentao_creator_name`
- `zentao_sync_message`
- `zentao_raw_payload`

它们应该降级为：

- 缓存字段
- 接口失败回退字段
- 同步痕迹字段

### 4.4 哪些锚点字段必须补齐

你现在的方案里最需要补齐的是“非 Bug 对象锚点”。

建议新增或显式化以下锚点：

#### 软件/产品层

建议在 `software_products` 增加：

- `zentao_product_id`
- `zentao_product_name_cache`

原因：

- 当前系统已有 `software_id`
- 禅道的产品维度要和本地软件维度建立稳定映射

#### 大版本层

建议在 `versions(version_type=major)` 增加：

- `zentao_project_id`
- `zentao_project_name_cache`
- 可选：`zentao_product_id`

原因：

- 你的大版本更像“某产品下的一条测试主线/项目主线”
- Stage5、报表、特派总表更适合按项目级接口批量取数

#### 小版本层

建议在 `versions(version_type=minor)` 增加：

- `zentao_execution_id`
- `zentao_execution_name_cache`
- `zentao_build_id`
- `zentao_build_name_cache`
- 可选：`zentao_release_id`
- 可选：`zentao_testtask_id`

原因：

- 你的“小版本/发包”概念在展示层更接近 Build
- 在测试周期层又更接近 Execution / TestTask
- 不能强行只映射到一个禅道对象

#### Requirement 层

建议在 `requirements` 增加：

- `zentao_story_id`（数值锚点）

保留：

- `zentao_req_id`（如 `r#5604`）

原因：

- 当前 `zentao_req_id` 是业务编号/展示编号
- 禅道详情接口走的是 numeric story id
- 仅靠运行时解析 `r#5604` 虽然能凑合，但长期不稳

#### TestCase 层

建议在 `test_cases` 增加：

- `zentao_case_numeric_id`

保留：

- `zentao_case_id`（如 `u#123`）

原因：

- 列表和详情接口里的 case id 形态不完全一致
- 统一保留“展示编号 + 原生 numeric id”最稳妥

### 4.5 对 bug_tracking 的建议不是删，而是瘦身定位

`bug_tracking` 不应该删除。

它应该明确转型为：

- 本地业务事实表
- 禅道对象定位表
- 禅道展示缓存表

建议保留并强化：

- 本地业务字段全部保留
- `zentao_bug_id / product_id / project_id / execution_id / requirement_id / linked_case_id` 保留
- 原有 title/name/url 类字段降级为缓存

如果你后面要新增字段，我建议优先补：

- `zentao_story_id`
- `zentao_build_id`
- `zentao_release_id`
- `zentao_testtask_id`
- `last_zentao_synced_at`
- `zentao_snapshot_json`（如果决定保留快照）

## 5. 页面级改造建议

## 5.1 我的工作台

保持不变的部分：

- 需求卡片结构
- 用例 / 自由 Bug 归属关系
- 用例完成 / 测试完成逻辑
- 本地新增 Bug、编辑 Bug、删除 Bug

建议新增的实时能力：

- Bug 标题实时显示
- Bug 当前状态、指派人、最后更新时间
- Bug 详情抽屉：步骤、历史动作、禅道链接、所属执行/Build
- Case 详情抽屉：标题、关联 Story、状态、最近执行信息

实现方式：

- 页面首屏仍走 `/requirements/my-workbench`
- 对当前卡片中的 bug 列表做懒加载 hydration
- 只对展开卡片或可视区卡片请求禅道详情

## 5.2 复测工作台

保持不变的部分：

- 复测通过/打回逻辑
- `is_retest_failed`
- 复测新增漏测 Bug

建议新增的实时能力：

- 原 Bug 当前禅道状态
- 当前是否已被关闭/解决
- 当前指派人是否变化
- Bug 最近动作

建议：

- 列表态先显示本地信息
- 点开某个需求卡片后再补充禅道明细

## 5.3 Stage5 总盘

这是最需要注意性能的页面。

原因：

- 该页可能挂很多 Bug
- 不能对所有行直接 `GET /bugs/{id}`

建议方案：

1. Stage5 首屏继续只用本地 `/stage5/overview`
2. 如果本地大版本已经配置 `zentao_project_id`，则后台或前端用 `/projects/{id}/bugs` 做范围级拉取
3. 只为当前可视行补充更多详情
4. 点某一行再请求 `/bugs/{id}` 展开完整详情

这样可以兼顾：

- 页面速度
- 数据实时性
- 不破坏现有闭环逻辑

## 5.4 特派页

保持不变：

- 用本地特派关系驱动
- 用本地 `closed / resolution / dispatched_to_id` 驱动状态

建议补充：

- 禅道当前状态
- 禅道当前指派人
- 最近动作
- 最近更新时间

这样管理员可以一眼看到：

- 本地特派给谁
- 禅道实际是不是已经转派或关闭

## 6. 技术实现建议

## 6.1 前端新增统一禅道客户端层

必须做统一客户端，不要在各页面散写 fetch。

建议拆成：

- `zentao-auth.js`
  - 登录禅道
  - 维护 token
- `zentao-client.js`
  - 原始 API 请求封装
- `zentao-normalizers.js`
  - 把不同接口返回归一化
- `zentao-cache.js`
  - 30~60 秒短缓存、去重、并发控制
- `zentao-hydrator.js`
  - 把本地 bug/case/requirement 对象补成可展示对象

### 6.2 Token 管理建议

建议：

- token 仅存浏览器 `sessionStorage`
- 不把禅道密码长期存到本地后端数据库
- 可选把 `base_url + account` 存到本地系统用户配置里
- 页面右上角提供“连接禅道 / 重新连接禅道”入口

### 6.3 响应归一化必须做

因为我已实测到：

- 同名字段在不同接口中可能是对象或字符串
- case id 可能是字符串壳子，也可能有单独 numeric 字段
- 成功状态码不一定总是 200

所以统一规范层里建议输出你自己的标准 shape，例如：

```json
{
  "bugId": 29875,
  "bugNo": "b#29875",
  "title": "...",
  "status": "active",
  "statusName": "激活",
  "assignedToName": "徐静",
  "openedByName": "顾靓燕",
  "productId": 15,
  "projectId": 134,
  "executionId": 1647,
  "storyId": 0,
  "openedBuild": "4.0.3.1.260413(40301023)",
  "stepsHtml": "...",
  "actions": [...],
  "url": "..."
}
```

### 6.4 列表页和详情页不要用同一种取数策略

推荐策略：

- 详情页/抽屉：`GET /bugs/{id}`、`GET /stories/{id}`、`GET /testcases/{id}`
- 范围列表页：优先用 `projects/{id}/bugs`、`executions/{id}/bugs`、`projects/{id}/builds` 这类范围接口
- 超大表：只给可视行做懒加载

### 6.5 初期不建议先新增数据库级大缓存表

你的原方案里提到 `zentao_bug_cache`。

我现在的建议是：

- 第一期先不上数据库缓存表
- 先做前端内存缓存 + session 缓存 + 页面级去重
- 只有当 Stage5 / 报表 / 特派总表性能不够时，再引入服务端缓存表

原因：

- 你现在最重要的是先把架构方向拉正
- 太早做数据库缓存，很容易又回到“镜像禅道”的旧路

## 7. 推荐改造路径

## 第一阶段：最小风险落地

目标：不动工作流，只补“实时展示能力”。

建议做法：

1. 新增前端禅道登录/token 管理
2. 新增前端统一禅道客户端

## 第四阶段：重新定义浏览器插件角色

目标：让插件继续有价值，但不再承担展示数据源角色。

建议做法：

1. 插件保留创建场景捕获

结合你当前系统结构和禅道实例的实测情况，我的最终建议是：

1. 不删除 `bug_tracking`、`test_cases`、`requirements`、`versions` 这些本地业务表。

结论：

> “构建记录入库后自动补建小版本”不是预备方案，而是现在就能修复实际数据断层的方案。

### 12.3 小版本自动生成建议直接挂在 Jenkins build-report 收包链路上

当前真实链路已经是：

- Jenkins/打包系统 -> `/api/admin/build-report`
- 后端 -> `BuildRecordService.upsert_report()`
- 前端构建记录页实时展示

因此最稳的做法不是新开一条同步链路，而是在 `build-report` 收包成功后，追加一个“版本自动归档”步骤。

建议规则：

1. 仅当 `build_status = SUCCESS` 时尝试自动建小版本
2. `version_name` 为空时不自动建版，只保留构建记录
3. 先把 `version_name` 归一化后再用于查重：
   - 去掉 `(64-bit)`、`(32-bit)` 之类平台尾缀
   - 去掉首尾空格
   - 保留中间的 `_alpha.1 / _BD / _Geofennel` 这类业务后缀
4. 从 `job_name` 解析目标大版本：
   - `s4031 -> V4.0.3.1`
   - `s40311 -> V4.0.3.11`
   - `s40311-1 -> V4.0.3.11`
   - 建议解析规则放宽到：`^s(\d{3,})(?:[-_].*)?$`
5. 查本地是否已有同名大版本
6. 若大版本存在，则在其下按 `version_name` 查重创建 `MINOR`
7. 若小版本已存在，则只更新构建记录，不重复创建
8. 若大版本不存在，建议先记一条“待归档构建”状态，不直接写错父级

这套规则与当前人工创建出来的小版本格式是对齐的，因为数据库中的现有小版本本来就是：

- `4.0.3.1.260407(40301016)`
- `4.0.3.1.260410(40301022)`
- `4.0.3.18.260413_Geofennel(40318007)`

也就是说：

> 自动建版应复用你现在的命名格式，而不是额外发明一个“构建记录专用格式”。

### 12.4 构建记录页本身也要做一处规则修正

前端 [build-records.js](/E:/APPAUTO/APPAuto/frontend/js/tabs/build-records.js:65) 现在的 `jobNameToMajorLabel()` 只识别严格的 `s数字`。

这会导致：

- `s4031` 可以显示成 `V4.0.3.1`
- `s40311-1` 这类带后缀的 job 不能正确显示和归档

所以方案里应补一句：

- 构建记录页和后端自动归档都必须使用同一套 `job_name -> major version` 解析器
- 解析器必须兼容 `-1`、`_free`、后续可能出现的渠道后缀

否则会出现“后端能归档、前端看起来却不像同一个大版本”的认知割裂。

### 12.5 浏览器插件应改成“过渡期保留，目标下线”

你已经明确希望后续废弃浏览器插件，这个方向是正确的。

结合当前现状，我建议把插件退场拆成 3 步：

1. 第一阶段：插件继续保留，只作为兜底和历史兼容入口
2. 第二阶段：当 `bug / story / testcase / execution / build / testtask` 都能在测试管理系统内直接读取展示后，停止新增插件能力
3. 第三阶段：当历史依赖页面完成替换后，下线 `/api/zentao/browser-sync` 及其前端同步中心入口

对你现在这套系统来说，插件最早可以退场的前提是：

- 需求详情能实时展示 story/testcase
- Bug 详情能实时展示 bug/execution/openedBuild/actions
- 构建记录能自动生成小版本
- 每个账号都有自己的禅道绑定，不再依赖手工粘贴 token 或浏览器态

所以它不应该被“立即删除”，而应该被“完成替换后下线”。

### 12.6 用户账号绑定禅道账号应做成“个人绑定 + 自动续 token”

当前本地 `users` 表只有：

- `username`
- `display_name`
- `password_hash`
- `role`
- `session_token`

并且现有接口里：

- 只有管理员能改 `display_name`
- 只有 `/auth/password` 是个人自助
- 没有“我的外部账号绑定”这一层

所以这块不能只加几个字段糊在 `users` 表上，建议单独设计绑定表，例如：

- `user_zentao_bindings.id`
- `user_id`
- `base_url`
- `zentao_account`
- `zentao_password_ciphertext`
- `zentao_password_iv`
- `token_value`
- `token_expires_at`
- `last_refresh_at`
- `last_refresh_status`
- `last_error_message`
- `created_at`
- `updated_at`

这里的关键取舍是：

1. 如果你要“token 失效后自动重新请求”，系统就必须持有可恢复的禅道登录凭据
2. 这意味着不能只存 hash，必须存“可解密密文”
3. 因此需要增加服务端加密密钥配置，例如 `APP_ZENTAO_BINDING_SECRET`
4. 前端和日志里都绝不能回显明文密码

推荐交互：

- 每个用户在“我的账号/个人设置”里维护自己的禅道绑定
- 可以修改 `禅道地址 / 账号 / 密码`
- 可以手动点“测试连接”
- 平时业务页只拿当前登录用户的绑定去取 token
- token 失效时，后端自动重新 `POST /v1/tokens`
- 若刷新失败，则提示该用户更新绑定，不影响其他用户

这比全局共用一个禅道账号要稳得多，因为：

- 权限更贴近实际使用人
- token 失效互不影响
- 后续如果禅道按人记录操作/权限，映射关系也更自然

### 12.7 方案收敛后的最终版本定义

结合你最新补充，Survey Master 这条线建议正式收敛成下面这套定义：

- 本地系统仍然是主工作流系统
- `project 134` 是查询范围，不是本地大版本对象
- 本地大版本 = 禅道 `execution`
- 本地小版本 = 发包 Build 的本地归档结果
- `testtask` 用于补充测试任务上下文
- `story/testcase` 负责补充需求和用例详情
- `bug` 负责补充缺陷详情
- 浏览器插件进入过渡期，目标是被 API 读取层替代
- 每个测试管理系统账号单独绑定自己的禅道账号，并由后端自动续 token

如果只保留一句最关键的改造原则：

> 不改你现有工作流主结构，只把“禅道真实对象层”接进来；其中 `execution` 接到大版本，`build` 接到小版本，`story/testcase/bug/testtask` 负责把详情补满。
